\section*{序章：三个智能体会更快吗}
\phantomsection
\addcontentsline{toc}{section}{序章：三个智能体会更快吗}

放学后的活动室里，Producer 把笔记本电脑转向广。

训练记录系统的登录模块从下午开始报错。问题不只在一个文件里：后端的权限判断需要检查，前端调用可能要跟着改，旧测试还没有覆盖越权访问。明天早上，这套系统又要继续使用。

Producer 在 Claude Code 里输入：

\begin{quote}
检查训练记录系统的登录模块，修复权限漏洞，更新相关调用，并补齐测试。不要破坏现有接口。
\end{quote}

终端没有立刻给出答案。它先读取项目规则，搜索认证入口，打开几个文件，然后运行测试。测试失败后，它又回到代码里。

「它还没有开始修吗？」

广轻轻点头。

「已经开始了。」

「可是文件还没有变化。」

「它在确认，要改的是哪里。还有，哪里不能改。」

几轮工具调用以后，终端里多出一条失败日志。后端权限判断、前端调用和回归测试，像三条岔路一样同时露了出来。

「那就开三个智能体，一人一条？」

广看着屏幕，停了一会儿。

「先别急。」

「不能并行？」

「可以。只是三个人同时改一个接口，也会更快地坏掉。」

她把 Producer 的笔记本拉近一点。

「先看清楚，问题是怎样分叉的。然后再决定，哪些路可以交出去。」

\section*{引言：一个复杂任务}
\phantomsection
\addcontentsline{toc}{section}{引言：一个复杂任务}

用户看到的输入只有一句话：

\begin{lstlisting}[caption={贯穿全文的复杂任务}]
检查训练记录系统的登录模块，修复权限漏洞，
更新相关调用，并补齐测试。不要破坏现有接口。
\end{lstlisting}

终端最先出现的却不是补丁，而是几项很平常的动作：

\begin{lstlisting}[caption={请求进入后最初留下的执行轨迹}]
Read   CLAUDE.md
Grep   "authorize|canAccess"  src/ tests/
Bash   pnpm test auth
       -> 1 failed, 18 passed
\end{lstlisting}

规则说明改动要怎样验收；搜索把“登录模块”落到具体文件；失败测试则告诉模型，原来的行为并没有想象中可靠。接下来的动作都很小：读一段、跑一次、看结果，再决定下一步。读取文件、运行命令、记录结果和拦住副作用的工作由外围 Harness 接手，许多次模型调用才连成一段工程过程。\cite{ch03e2e,ch03dive}

\FloatBarrier

\section{任务先从哪里开始}

回车之后，Claude Code 没有马上改文件。它先把当前目录、项目规则、测试命令和权限模式摆到桌面上。这份快照很小，却会一直约束后面的动作：\cite{ch03e2e,ch03agents}

\begin{lstlisting}[caption={认证任务的会话边界示意}]
cwd          /repo/training-log
project rule keep public auth API compatible
test command pnpm test auth
permissions  read/search: allow; edit/bash: check
\end{lstlisting}

于是，“登录模块”有了落脚点：搜索从当前仓库开始，修复必须保留公共接口，验收要使用项目自己的测试命令；模型若提出编辑或执行命令，Harness 还要按权限模式决定放行、询问或拒绝。换一个目录，或者换一份 \texttt{CLAUDE.md}，同一句话就会从另一个位置开始。

这些边界还在程序里，模型暂时看不见。下一轮输入要把它们摆到模型眼前。

\section{模型究竟看到了什么}

模型真正收到的东西，已经远不止用户的那句话。前面是较稳定的系统行为、项目规则和工具 schema；后面是这次任务，以及刚刚发生的观察。排查继续以后，前面大多不变，后面却会被搜索结果、Diff 和测试日志一点点拉长。

现在模型手里有了环境，却还不知道漏洞藏在哪个入口。下一步只能先挑一个仓库能回答的问题。

\section{一个大目标，怎样拆成几步}

面对这句完整要求，Claude Code 没有先猜补丁。它先补了一个会失败的越权用例：只有“本应返回 403，却得到 200”真的出现，权限漏洞才从一句描述变成眼前的事实。

排查顺序也随之清楚起来：先找到请求入口和权限判断，再确认公共接口不能变；后端修复与调用方搜索可以分开做，最后还得回到同一组测试里碰头。

\section{失败日志出现以后}

第一次测试刚跑完，计划就被改了两次。新增的攻击测试先证明漏洞存在；后端补上资源所属校验以后，攻击测试转绿，旧的前端兼容测试却开始失败：调用方一直依赖后端接受缺失的资源标识。

\begin{lstlisting}[caption={两次失败怎样改变问题}]
authz.spec.ts    expected 403, received 200
                 -> 漏洞得到复现

session.spec.ts  expected legacy request to succeed
                 -> 后端修复暴露调用方旧假设
\end{lstlisting}

测试结果一次只照亮一小块地方。结果回来，模型才知道该读哪个文件、改哪一行，或者再跑哪条命令；Harness 检查权限、执行动作，再把内容、Diff、退出状态或错误送回下一轮 Prompt。单个 Agent 就这样一圈一圈地往前走：

\subsection{大模型如何解决复杂问题}

到了第三轮，麻烦全都落到了具体地方：攻击测试要先失败，补丁才有目标；宽泛搜索和长日志开始挤占对话；调用方扫描与攻击测试可以分头推进；后端和前端却共用一份接口约束。把这些麻烦分开看，会得到四种不同的复杂性：

这里没有什么“一次想通”。它只是把眼前的目标缩成下一项能检查的动作，再让工具结果把自己拉回来；等旁支已经能带着清楚的任务和结果独立交卷，另开一条循环才开始划算。

「现在可以开三个了吗？」

「两个。」

「少的那个呢？」

「接口约束留在这里。不能一起丢出去。」

\section{什么时候该叫来另一个智能体}

在父 Agent Loop 的工具菜单里，\texttt{Agent} 和 Read、Grep、Bash 一样，先只是一项可调用的工具。父模型发出 Agent tool call，Harness 才会另开一段上下文，配上模型和工具；那段工作结束后，报告或完成通知再回到父循环。换句话说，多智能体不是突然换了一套世界，而是一次工具调用又打开了一个 Loop。\cite{ch03multi,ch03dive,ch03subagents}

要不要开这条新循环，先问两个实际问题：这一步是否必须接着眼前的推理做？它是否需要父会话已经积累的背景？

\FloatBarrier

\subsection{先决定从哪一段记忆开始，再决定谁来做}

Fork 与 Fresh 只回答“从哪里开始”。Fork 接着父会话已有的对话往下走，省掉背景重述，却也会把旧噪声一起带过去；Fresh Agent 从一张干净的任务单开始，少了杂音，但遗漏的约束不会自动回来。Prompt cache 能让共享的稳定前缀便宜一点，子智能体的生成、工具调用和最后的汇总仍然要付费。\cite{ch03multi,ch03cache}

选了 Fresh，还要再决定“让谁做什么”。Explore、Plan、通用 Subagent、项目自定义 Agent 与 Teammate 说的是角色和工具；Worktree 说的是文件放在哪儿。它们不是同一个开关：能不能继承旧对话、能不能写文件、能不能持续通信，要分开看。

这次父循环只发出两张清单：Explore 搜索前端所有认证调用，只报告请求形状和还没确认的地方；测试 Subagent 只补边界用例，带回 Diff 和测试命令。公共接口仍由父循环掌握，没有第三个人同时设计它。

两张清单回来以后，调用方搜索和攻击测试确实可以并行。可一旦两边都要写代码，另一个问题就冒出来了：对话分开了，文件和运行环境还没有。

\clearpage
\section{并行之后，谁负责什么}

测试 Subagent 和父循环现在各有一段对话，搜索噪声不会直接混在一起。可要是两边还指向同一个 checkout，父循环改 \texttt{authorize.ts} 时，子循环也在写测试文件，双方看到的仍是同一份未提交状态。对话分开了，源码还没有。

\subsection{对话分开了，文件和服务呢}

Git worktree 把两个写入分支放进不同工作副本。父循环在 \texttt{fix/authz} 收紧后端校验，子循环在 \texttt{test/callers} 更新调用方和测试。两边共享 Git 对象与历史，未提交文件互不覆盖，最后再经过同一个合并门。\cite{ch03multi,ch03worktrees,ch03dive}

如果两个测试同时重置同一个测试用户，或争用同一端口，源码没有互相覆盖，结果仍可能随机失败。真实团队的经验也提醒了这一点：Worktree 解决 working copy，数据库与开发服务要另外命名、复制或串行使用。\cite{ch03trigger}

放回这次认证任务，分工就很具体：Explore 只需要一段独立对话；写测试的 Subagent 需要自己的工作副本；并行测试要用不同的数据库名字；公共认证接口则只能有一个人拍板。最后一条没有人负责，即使两个 worktree 都很干净，也可能各自交回一套不兼容的设计。

\subsection{两个智能体需要直接说话吗？}

刚才两份派工各自向父循环交卷就够了：父节点给出范围和验收条件，worker 带着结果回来，两个 worker 之间没有必要互相聊天。这样的父子汇总已经足够。

如果前端扫描发现“资源标识”根本拿不到，而后端又必须据此调整契约，两边才值得直接交换消息、更新共享任务状态、解除彼此的等待。此时可以升级成 Agent Teams 的持续协作；代价也很实际：消息、任务状态和成员的开始与结束，都要有人维护。\cite{ch03multi,ch03teams}

\subsection{只把下一步需要的东西交出去}

Explore 的几百行搜索过程可以留在自己的记录里；但“前端必须补充资源标识”会改变后端下一步，就应该写进报告、共享任务或消息。自己的记录保留推理细节，大家共享的地方只放契约、依赖、完成条件和能复查的结果。

成员完成后，父循环还要接收报告，检查有改动的 worktree，保留要合并的分支并清理空工作区。若任务跨过关机或会话结束，运行中的成员不能被当作持久记忆；角色、承诺、进度和未决消息需要写入可恢复的外部状态。\cite{ch03atwz}

多开几个智能体，也不会凭空多出几份可靠结果。相同的任务、相同的工具路径和相同的验证方法，可能只是把同一种错误重复几遍。

「三个智能体都显示任务完成了。」

「嗯。」

「这次总可以相信了吧？」

「三份相同的完成报告。不是三份证据。」

\FloatBarrier

\section{怎样知道事情真的做完了}

屏幕上出现两条“完成”时，原任务里的四个动词还在：检查、修复、更新、证明。Explore 找到调用方，测试 Subagent 交回攻击用例，都只做完其中一部分。父循环要在合并后的工作树里重新检查接口约束，再让 verifier 用越权输入和旧调用方式各试一次。

智能体说“测试通过”还只是下一轮要看的材料。命令在哪个目录跑的、退出状态是什么、关键日志留下了什么，都要重新看一遍。实现者沿着设计路径确认补丁能工作，verifier 则从“资源不属于当前用户”“标识缺失”“旧客户端请求”等边界反过来试着弄坏它。\cite{ch03dive,ch03atwz}

\section{结论：把证据送回最初的问题}

回看这次排查，规则文件、失败测试、旁支报告和合并后的命令结果，刚好一件接一件地接上了最初的验收条件。旁支只有在任务边界、文件所有权和返回结果都说得清时才值得交出去；回来以后，仍要在同一组测试前重新报到。

\begin{samepage}
活动室里，全量测试终于结束。Producer 看着终端里绿色的退出状态，松了一口气。

「这次是真的完成了？」

「认证测试通过了。调用方通过了。旧接口也还在。」

「所以是。」

「所以，在这个仓库里，是。仓库外的客户端，还没有证据。」

「你一定要加最后一句吗？」

「嗯。边界清楚，比较安心。」

她合上笔记本，动作很慢。

「而且，下次可以把任务再难一点。」

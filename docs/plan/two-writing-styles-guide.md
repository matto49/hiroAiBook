# 两种技术同人写作风格整理

## 文档定位

这份文档用于固定两种可复用的文章组织方式：

1. 喜剧小说＋技术报告；
2. 对话式教材。

当前阶段只总结既有文章的结构、节奏和技术内容编排方法，不预设后续文章的题目、情节或技术结论。正式编写前，应先由使用者提供主题、材料和必要边界，再依据本文进行结构化。

## 分析样本

本文基于以下五篇现有文章整理：

1. `向筱泽广请教多臂老虎机问题`
2. `羽毛球与天气 - Runge-Kutta 法 -`
3. `26%的误差`
4. `一切皆为回响：关于蒙特卡洛法与模拟退火`
5. `和补习组一起学习泊松分布`

五篇文章并不是完全统一的文体，而是共享“角色化技术同人”框架的不同实现：

| 文章 | 主要形态 | 分析用途 |
| --- | --- | --- |
| 多臂老虎机问题 | 对话式教材 | 标准教学循环、算法递进、练习题 |
| 羽毛球与天气 | 场景融合型对话教材 | 日常事件与技术问题互相推动 |
| 26%的误差 | 喜剧小说＋技术报告 | 小说外壳、集中推导、现实回收 |
| 蒙特卡洛法与模拟退火 | 高密度技术独白 | 用于识别术语过密和单向讲授问题 |
| 泊松分布 | 漫画式压缩教材 | 用画面、误解和公式快速完成教学 |

## 共同写作原则

无论使用哪一种风格，都应满足以下原则。

### 技术内容由问题推动

文章不按论文年代、术语列表或知识百科的顺序铺开，而是形成问题链：

```text
现实问题
→ 初步方案
→ 发现方案缺陷
→ 引入新概念
→ 解决当前缺陷
→ 暴露下一层问题
```

新的概念应当在旧方法无法继续时出现。若删掉一个概念后，故事中的问题仍能照常解决，那么该概念可能并非本篇必需。

### 日常场景不是包装

开头出现的物件、任务或矛盾，应进入后续模型：

- 日常对象成为变量或状态；
- 人物需求成为目标函数；
- 现实限制成为约束；
- 人物的误解成为待纠正的直觉；
- 最终计算结果改变人物的行动。

如果场景只在开头出现一次，随后整篇都可以替换成普通讲义，那么场景尚未真正参与文章。

### 公式必须经过两次翻译

每个重要公式至少完成两次解释：

1. 解释符号分别代表什么；
2. 把完整公式重新翻译成自然语言。

公式之后还应通过数值例子、边界条件或人物复述确认理解，不能只用一句“原来如此”结束。

### 角色声音附着于判断

技术事实本身不需要强行角色化。角色感主要体现在：

- 为什么注意到这个问题；
- 如何选择简化条件；
- 对失败、误差和困难作何评价；
- 是否接受当前答案；
- 下一步决定做什么。

广不应被写成只会播报术语的知识机器。她更适合轻声说出准确、直接、略显异常但逻辑完整的判断。

### 数学正确不等于现实完整

文章可以让模型失败，但应区分：

- 计算错误；
- 实现错误；
- 参数错误；
- 假设不成立；
- 模型没有回答现实真正关心的问题。

更适合这套风格的收束通常是：

> 数学在自己的前提下没有错，但现实提出了一个尚未写进模型的问题。

## 风格一：喜剧小说＋技术报告

### 核心结构

这类文章使用三段式嵌套：

```text
日常喜剧开场
→ 集中的技术报告
→ 回到现实完成喜剧回收
```

它不是简单地在小说中插入科普。开场问题必须能够被正式建模，技术报告的结论也必须直接参与结尾事件。

### 第一阶段：日常问题

开头负责建立以下信息：

- 谁遇到了问题；
- 对方具体想实现什么；
- 为什么这件事需要广参与；
- 广如何把普通问题识别成技术问题；
- 哪个看似合理的前提将被带入模型。

此阶段以人物动作、环境和短对白为主，不急于解释完整知识。需要让读者先理解人物到底想做什么。

### 第二阶段：问题转化

故事进入技术报告前，需要完成一次清晰的“翻译”：

| 日常层 | 技术层 |
| --- | --- |
| 人物想实现的结果 | 优化目标或待求量 |
| 可选择的行动 | 决策变量 |
| 时间、空间、体力等限制 | 约束条件 |
| 对现实的简化 | 模型假设 |
| “最好”“最多”“最可能” | 评价指标 |

转换完成后，文章才进入正式报告。不能在读者还不清楚问题含义时直接堆出公式。

### 第三阶段：技术报告

技术报告可采用较客观、正式的语体，并按以下顺序组织：

1. 问题定义；
2. 已知条件；
3. 简化假设；
4. 符号和变量；
5. 数学模型或算法；
6. 推导、模拟、实验或代码；
7. 不同方案的结果比较；
8. 技术结论；
9. 局限说明。

报告部分可以出现：

- 公式；
- 算法步骤；
- 表格；
- 程序；
- 实验参数；
- 结果图；
- 脚注与参考文献。

但其中至少要保留一项将在结尾发挥作用的边界，例如：

- 被忽略的现实变量；
- 默认成立但未经验证的前提；
- 只在特定参数或起点下成立的结果；
- 目标函数没有包含的人物需求；
- 模型无法描述的实际操作。

这项边界不是为了证明报告错误，而是让结尾能够重新评价报告的适用范围。

### 第四阶段：现实回收

报告结束后，叙事重新回到人物场景：

1. 广宣布或展示技术结论；
2. 问题提出者准备接受或执行；
3. 现实条件、另一名角色或实际操作暴露遗漏；
4. 前面的复杂答案被重新理解；
5. 人物作出新的决定。

理想的喜剧效果来自：

- 复杂计算与简单现实之间的错位；
- 广的过度认真；
- 结果虽然正确，却没有完全解决生活问题；
- 其他角色无意间指出了模型边界。

结尾不应简单宣布“数学没有用”。更好的结果是让技术结论仍然成立，同时承认问题需要重新定义。

### 人物分工

#### 问题提出者

- 带来具体、生活化的需求；
- 说明自己真正关心的结果；
- 在技术报告结束后尝试执行结论。

#### 广

- 识别问题结构；
- 提出必要假设；
- 完成计算或组织实验；
- 对困难和复杂化保持异常平静的兴趣；
- 在边界暴露后重新评价问题。

#### 第三方或现实事件

- 提供模型没有纳入的信息；
- 不是为了嘲笑广，而是让问题回到真实环境；
- 推动人物决定下一步如何修改模型或目标。

#### 旁白

- 维持轻小说式场景；
- 放大问题规模与认真程度之间的反差；
- 在技术报告前后负责语体切换；
- 不代替人物解释技术结论。

### 建议篇幅比例

| 部分 | 建议比例 |
| --- | ---: |
| 日常开场 | 15%～20% |
| 问题转化 | 约 10% |
| 技术报告 | 45%～60% |
| 现实回收 | 15%～20% |
| 脚注或后记 | 可选 |

比例并非硬性要求。判断标准是：报告再长，读者仍然记得人物为什么要计算这件事。

### 转场方法

从小说进入报告时，应有明确的认知动作：

- 广开始整理已知条件；
- 人物拿出笔记、终端或实验数据；
- 叙述说明接下来固定变量和假设；
- 日常对象被替换为数学符号。

从报告回到小说时，应有明确的执行动作：

- 计算结束；
- 程序输出结果；
- 人物准备按结论行动；
- 第三方进入；
- 现实实验开始。

避免毫无提示地在小说段落和论文段落之间切换。

### 常见失误

- 技术报告与开头问题没有直接关系；
- 结尾反转是随机事件，而不是模型边界的结果；
- 故意使用错误计算制造笑点；
- 报告结束后没有人物行动；
- 结尾把技术结论整体否定；
- 反复依赖病弱、晕倒或保健室作为唯一笑点；
- 技术部分太长，人物关系完全停滞。

### 完成检查

- [ ] 开场需求可以用一句话说清。
- [ ] 日常对象与数学变量能够一一对应。
- [ ] 报告明确列出假设和约束。
- [ ] 技术结论在给定前提下成立。
- [ ] 结尾回收的是前文已有边界。
- [ ] 现实反转没有否定全部技术价值。
- [ ] 广的认真来自人物性格，而不是作者强迫她讲课。

## 风格二：对话式教材

### 核心结构

这类文章不设置独立的报告层。技术内容始终由对话和问题递进承担：

```text
现实问题
→ 直觉回答
→ 暴露漏洞
→ 定义概念
→ 引入公式
→ 用例子验证
→ 发现新问题
→ 引出下一种方法
→ 总结、练习或实际决策
```

新的方法不是并列罗列，而是作为前一个方法缺陷的回答出现。

### 最小教学循环

每个知识点可以使用以下循环：

1. 广提出一个具体问题；
2. 学习者按照已有直觉回答；
3. 广确认回答中正确的部分；
4. 指出尚未解决的条件；
5. 给出术语、定义或公式；
6. 逐个解释符号；
7. 把公式翻译成自然语言；
8. 学习者重新复述或计算；
9. 使用数值例子、反例或边界情况验证；
10. 由结果引出下一轮问题。

并非每轮都必须完整写出十步，但“直觉—修正—形式化—验证”四个阶段应当存在。

### 整篇技术顺序

较稳定的长篇结构如下：

1. 现实任务与问题定义；
2. 基础术语；
3. 符号约定；
4. 最简单的基线方法；
5. 基线方法的算法步骤；
6. 具体例题；
7. 基线方法的优缺点；
8. 从缺点引出改进方法；
9. 方法比较；
10. 实际选择、练习或作业。

如果主题只有一个核心概念，可以缩短为：

```text
误解
→ 定义
→ 公式
→ 数值例子
→ 反直觉结果
→ 应用
```

### 对话角色分工

#### 广

- 负责观察问题结构；
- 用问题确认对方的理解；
- 确认回答中正确的部分，再指出缺口；
- 只在需要时引入术语；
- 解释公式的自然语言意义；
- 说明哪些细节暂时省略，以及省略原因；
- 对失败、误差和例外表现出兴趣。

广不能连续数页只负责播报知识。她的角色性应体现在判断、取舍和对困难的评价中。

#### 学习者

- 是读者的理解代理；
- 可以不知道术语，但应具备正常的推理能力；
- 能够复述刚刚学到的内容；
- 偶尔发现边界问题、除零情况、参数缺失或直观反例；
- 把抽象公式重新拉回现实任务；
- 在结尾根据所学内容作出选择。

学习者不能长期只说：

- “原来如此”；
- “完全不懂”；
- “广好厉害”；
- “接下来呢”。

若学习者的台词删掉后，教学逻辑完全不变，说明对话仍然只是讲义外壳。

### 公式与对白节奏

推荐的基本节奏是：

```text
两到四轮短对白
→ 一个定义、公式或说明块
→ 一轮自然语言复述
→ 一个例子或问题
→ 回到短对白
```

具体要求：

- 每次只增加少量新符号；
- 新符号在首次出现时定义；
- 长公式前说明“为什么现在需要它”；
- 长公式后说明“它回答了什么”；
- 数值例子优先使用开场问题中的对象；
- 较长推导中插入理解确认、人物动作或短暂停顿；
- 不用角色对白重复朗读已经清楚的整段报告文字。

### 方法递进

多个算法或方法之间应形成因果关系：

```text
方法 A 能解决基础问题
→ 例子暴露 A 的缺陷
→ 学习者提出改进方向
→ 方法 B 将该方向形式化
→ 新例子暴露 B 的适用边界
```

不建议使用：

```text
方法 A 的定义
→ 方法 B 的定义
→ 方法 C 的定义
→ 三者总结
```

后一种形式容易变成综述，不容易形成课堂感。

### 场景维持

虽然主体是教材，对话仍然发生在具体时间和地点。场景需要定期回到文本中：

- 人物正在操作什么；
- 当前例子来自哪里；
- 计算是否改变现场决定；
- 广或学习者的身体和注意力状态如何；
- 课程结束后要做什么。

场景回归不需要频繁描写环境。一个动作、一次实际输入或一次结果输出，就可以把课堂重新接回现实。

### 结尾方式

对话式教材不必强行反转，可以采用：

- 一道作业；
- 一个尚未解决的问题；
- 让学习者作出实际决策；
- 用新方法重新处理开场问题；
- 暴露下一讲需要解决的缺陷；
- 结束课程并进入现实行动。

结尾必须表明本篇知识改变了什么，而不只是“今天学到了很多”。

### 常见失误

- 形式上使用引号，实质仍是广的长篇论文独白；
- 学习者被写成没有推理能力；
- 问答只是为了机械引出术语；
- 日常场景只在第一页出现；
- 公式没有符号说明和自然语言解释；
- 按技术史或论文顺序罗列知识；
- 对话只负责夸奖，不承担理解推进；
- 每个知识点都讲到同样深度，缺少取舍。

### 完成检查

- [ ] 开场存在读者能理解的现实问题。
- [ ] 技术概念按照问题链出现。
- [ ] 每个主要公式都解释了符号和整体含义。
- [ ] 学习者至少完成一次有效复述或推理。
- [ ] 新方法用于解决旧方法暴露出的缺陷。
- [ ] 场景在技术讲解中持续产生作用。
- [ ] 结尾回到实际决定、练习或下一问题。
- [ ] 广的对白保持短、轻、直接，少用感叹号。

## 两种风格的区别

| 项目 | 喜剧小说＋技术报告 | 对话式教材 |
| --- | --- | --- |
| 主要动力 | 情节与现实反差 | 问题和理解递进 |
| 技术呈现 | 集中的正式报告 | 分散在连续对话中 |
| 旁白比例 | 较高 | 较低 |
| 对话功能 | 建立人物、提出问题、回收结果 | 承担教学逻辑 |
| 技术结尾 | 暴露模型边界 | 总结、练习或引出新方法 |
| 喜剧来源 | 复杂答案与简单现实错位 | 理解误差和角色反应 |
| 适合内容 | 有计算、模拟、实验或方案比较的问题 | 有多个递进概念或算法的问题 |

## 不应混淆的第三种声音

样本 PDF 中还存在译者注或编辑吐槽。其常见特点是：

- 网络化口语；
- 快速概括整篇；
- 直接评价角色或算法；
- 把技术内容压缩成一个笑话。

这类文字不属于广的对白，也不属于正文旁白。后续如需保留，应明确放在：

- 译者注；
- 页边批注；
- 章末后记；
- 独立漫画说明。

不应把这种语气直接混入正文，否则会破坏人物气氛和技术叙述的可信度。

## 后续编写流程

收到新内容后，按照以下顺序工作：

1. 整理使用者提供的事实、公式、来源和剧情素材；
2. 区分“必须保留”“可以简化”“不能自行补充”的内容；
3. 选择写作风格；
4. 先产出结构，不写正文；
5. 检查技术问题链或报告链是否完整；
6. 检查角色行动是否与技术内容相连；
7. 由使用者确认结构；
8. 再进入正文编写；
9. 完成后核对技术事实、角色声音和 LaTeX 结构。

在结构确认前，不自行发明：

- 技术主题；
- 论文结论；
- 实验数据；
- 角色关系事件；
- 结尾反转；
- 必须由使用者决定的价值判断。

## 最终判断标准

一篇完成稿至少要同时通过三项检查：

### 技术检查

- 问题定义明确；
- 公式和结论在给定前提下成立；
- 假设、参数和适用范围可见；
- 没有为了剧情方便而伪造技术因果。

### 结构检查

- 每一节都回应当前问题；
- 新知识由上一层缺陷引出；
- 开场对象参与后续模型；
- 结尾回收前文已有条件。

### 角色检查

- 广保持安静、清醒、直接；
- 她对困难的兴趣有明确对象，不是空洞受苦；
- 学习者具备正常推理能力；
- 人物关系推动技术问题，而非只给讲义套名字。

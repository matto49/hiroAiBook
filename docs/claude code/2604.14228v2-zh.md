## 摘要

Claude Code 是一种智能体式编程工具，可以代表用户运行 shell 命令、编辑文件并调用外部服务。本研究通过分析公开可得的 TypeScript 源码，描述其完整架构；同时将其与两个独立的开源 AI 智能体系统 OpenClaw 和 Hermes Agent 比较。这两个系统处于不同部署情境，却需要回答许多相似甚至相同的设计问题。

我们的分析识别出推动该架构形成的五项人类价值、理念与需求：人类决策权威，安全、安全防护与隐私，可靠执行，能力放大，以及情境适应性。随后，我们通过十三项设计原则，将这些价值追踪到具体实现选择。系统核心只是一个简单的 `while` 循环：调用模型、运行工具，然后重复。不过，大部分代码其实位于这个循环周围的系统中：包含七种模式和机器学习分类器的权限系统；用于上下文管理的五层压缩流水线；MCP、插件、技能与钩子四种扩展机制；子智能体委派与编排机制；以及以追加写入为主的会话存储。

与 OpenClaw（多通道个人助理网关）和 Hermes Agent（单进程、多交互表面的助理）的比较表明，同一组设计问题在三种部署情境下会产生不同答案。Claude Code 强调逐操作安全；OpenClaw 强调边界层访问控制；Hermes 则在多种交互表面呈现逐操作审批。在运行时层，Claude Code 使用单一 CLI 循环，OpenClaw 将运行时嵌入网关控制平面，Hermes 使用由入口点决定角色的单进程。在上下文与扩展层，Claude Code 扩展上下文窗口，OpenClaw 注册网关范围的能力，Hermes 提供可插拔的记忆与模型后端。最后，我们依据近期实证、架构与政策研究，提出未来智能体系统的六个开放设计方向。

## 1 引言

AI 辅助软件开发已经从 GitHub Copilot（Chen et al., 2021）一类自动补全工具，经由 Cursor（Cursor, 2026）等 IDE 集成助手，演进到能够自主规划多步骤修改、执行 shell 命令、读写文件并对自身输出迭代的完整智能体系统。Claude Code（Anthropic, 2026a）是 Anthropic 发布的智能体式编程工具（Anthropic, 2026e）。其官方文档把它描述为一个“智能体循环”：围绕目标规划并执行操作，调用工具、评估结果，直到任务完成。¹

从“给出建议”转向“自主行动”，带来了自动补全工具从未面对的架构要求。这些要求共同定义了一个设计空间：安全、上下文管理、可扩展性、委派等所有编程智能体都必须处理的反复出现的问题。本研究通过对 Claude Code 的源码级分析，展示一个生产系统如何回答这些问题。尽管 Claude Code 已广泛采用，Anthropic 发布的是面向用户的文档，而不是详细架构说明，因此本文以源码分析来描述其架构设计决策。

Anthropic 对 132 名工程师和研究人员的内部调查（Huang et al., 2025）发现，Claude Code 辅助任务中约 27% 是没有该工具便不会尝试的工作。这说明架构带来的不只是对现有工作加速，还包括性质上全新的工作流。

本文先识别推动架构形成的五项价值/理念和十三项设计原则（第 2 节），再从三方面组织分析：

1. **设计空间分析。** 识别反复出现的设计问题：推理位于何处、迭代循环如何组织、采用何种安全姿态、如何划分扩展表面、如何管理上下文、如何把工作委派给子智能体，以及会话如何持久化。随后通过七组件高层结构和五层子系统架构分析 Claude Code 的答案，并将每项选择追踪到具体源码文件（第 3 节）。目标是深入理解系统机制，为更好、更强的智能体系统设计提供参考。
2. **与 OpenClaw、Hermes Agent 的架构对照。** 除 Claude Code 外，本文还在六个维度上比较 OpenClaw（Steinberger and OpenClaw Contributors, 2026）与 Hermes Agent（Nous Research, 2026），展示同一设计问题如何因部署情境不同而得到不同答案（第 10 节），从而揭示商业软件与开源软件的共同原则和关键差异。比较也有助于说明部署环境、产品目标、安全要求和用户假设怎样塑造架构选择。
3. **未来智能体系统的开放方向。** 在设计空间分析及系统对照的基础上，第 13 节提出六个开放方向：可观测性与评估之间的缺口、跨会话持久化、harness 边界演进、任务时域扩展、治理，以及开发者的长期能力。其中最后一点揭示出一个开放问题：Claude Code 能够放大程序员与终端用户的短期能力，却很少提供明确促进人类长期进步、深入理解和代码库持续一致性的机制。

核心智能体循环是带状态管理的无限循环；安全、可扩展性、上下文管理、委派与持久化等外围子系统占据了实现的大部分。源码级分析²使我们能直接从系统识别设计选择、子系统边界和实现权衡，而不是只依据产品描述推断。

**贯穿全文的例子。** 第 3 至第 9 节持续追踪同一任务：“修复 `auth.test.ts` 中失败的测试”。这个看似简单的请求会激活工具调用、权限检查、上下文选择、迭代修复、委派与会话持久化等多个架构层。

**论文结构。** 第 2 节说明推动架构形成的人类价值和设计原则；第 3 节介绍高层架构及其回答的设计问题；第 4 至第 9 节分别分析主要子系统；第 10 节与 OpenClaw、Hermes Agent 对照；第 11 节联系既有智能体与软件工程研究；第 12 节讨论；第 13 节梳理开放问题；第 14 节总结。附录说明证据基础、方法、包结构、社区重新实现，以及新智能体系统信号与本文设计空间问题之间的对应关系。

## 2 设计理念、设计原则与架构动机

生产级编程智能体由人构建、为人服务；其中嵌入的架构决策反映了创造者认为什么最重要。本节识别推动 Claude Code 设计的人类价值，通过反复出现的设计原则追踪这些价值，并提出组织第 3 至第 9 节分析的设计空间问题。

Anthropic 的安全智能体框架提出一个核心张力：“智能体必须能够自主工作；独立运行正是其价值所在。但人类应当保留对目标实现方式的控制”（Anthropic, 2025a）。Claude 宪法并非用刚性的决策程序解决它，而是培养“能够依情境运用的良好判断与健全价值观”（Anthropic, 2026b）。这些承诺，加上开发者实际使用工具的实证发现（Huang et al., 2025; McCain et al., 2026），指向塑造架构的五项人类价值。

### 2.1 五项价值与理念

**人类决策权威。** 人类保留对系统行为的最终决定权。其主体层级依次为 Anthropic、运营者和用户，从形式上规定谁对什么拥有权威（Anthropic, 2026b）。系统支持人类进行知情控制：实时观察操作；批准或拒绝拟议动作；中断兼容的执行中操作；事后审计。当 Anthropic 发现用户批准了 93% 的权限提示（Hughes, 2026）时，其回应不是增加警告，而是重构问题：用沙箱和自动模式分类器划出明确边界，让智能体能在边界内自由工作；而不是继续依赖用户习惯后便不再认真阅读的逐操作审批（Dworken and Weller-Davies, 2025）。

**安全、安全防护与隐私。** 即使人类注意力不足或犯错，系统也应保护人、代码、数据和基础设施免受损害。这与人类决策权威不同：权威关心人是否有选择能力；安全则关心当这种能力失效时，系统仍有保护义务。Anthropic 的安全智能体框架分别把保障智能体交互安全和保护长期交互中的隐私列为核心承诺（Anthropic, 2025a）。自动模式威胁模型（Hughes, 2026）明确针对四类风险：过度积极的行为、无意错误、提示注入，以及模型失准。

**可靠执行。** 智能体应执行人真正想要的事情，长时间保持一致，并在宣布成功前支持验证。它既涵盖单轮正确性（是否忠实理解请求），也涵盖长时域可靠性（跨越上下文窗口边界、恢复会话和多智能体委派后是否仍一致）。Anthropic 产品文档（Anthropic, 2026f）将其描述为反复执行直到任务完成的三阶段循环：收集上下文、采取行动、验证结果。智能体设计指南（Schluntz and Zhang, 2024）进一步强调每一步都要用“来自环境的 ground truth”评估进展。Harness 设计指南（Rajasekaran, 2026）也指出，即使质量平庸，“智能体也倾向于自信地赞扬自己的工作”，因此生成与评估应当分离。

**能力放大。** 系统显著提高人类每单位努力和成本所能完成的工作。第 1 节提到的 Anthropic 内部调查（Huang et al., 2025）说明，其架构不仅加速现有工作，也允许全新工作流：约 27% 的任务本来不会被尝试。创造者将该系统称为“Unix 工具，而非传统产品”，从“有用、易懂、可扩展”的最小构件构建（Cherny and Wu, 2025）。架构把资源投入确定性基础设施——上下文管理、工具路由和恢复——而不是显式规划器或状态图等决策脚手架。其前提是，能力不断增强的模型从丰富运行环境获得的收益，比从限制选择的框架中更大。

**情境适应性。** 系统应适配用户的具体情境，包括项目、工具、惯例与技能水平，并随时间改善人与智能体的关系。扩展架构（`CLAUDE.md`、skills、MCP、hooks、plugins）以不同上下文成本提供多级可配置性（第 6、7 节）。纵向数据（McCain et al., 2026）表明，人机关系会演化：使用少于 50 个会话时自动批准率约为 20%，到 750 个会话时超过 40%。这种被称作“由模型、用户和产品共同建构”的自主性，意味着系统面向信任轨迹设计，而非固定信任状态。MCP 捐赠给 Linux Foundation 旗下 Agentic AI Foundation（The Linux Foundation, 2025）也体现了该价值的生态维度。

### 2.2 设计原则

上述价值通过十三项设计原则落实；每项原则回答生产级编程智能体必须解决的反复问题。表 1 作了概括，第 3 至第 9 节会把它们追踪到具体实现。

这些原则可与三类主要替代设计比较。第一，基于规则的编排：LangGraph（LangChain, Inc., 2024）等框架用带类型边的显式状态图编码决策逻辑，选择脚手架而非最小 harness。第二，容器隔离执行：SWE-Agent 和 OpenHands（Yang et al., 2024; Wang et al., 2024b）主要依靠 Docker 隔离，而不是分层策略执行。第三，以版本控制保证安全：Aider（Gauthier, 2024）把 Git 回滚作为主要安全机制，而不是默认拒绝的权限评估。Claude Code 的独特之处，在于同时采用最小决策脚手架与分层策略执行、基于价值的判断与默认拒绝，以及渐进上下文管理与可组合扩展。

### 2.3 从价值到架构

每项价值都可沿相应原则追踪到具体架构决策：

- **人类决策权威**推动默认拒绝评估、渐进式信任谱系、可审计的仅追加状态、外部化可编程策略，以及价值优先于规则（第 5-7、9 节）。
- **安全、安全防护与隐私**推动纵深防御、默认拒绝、按可逆性加权的风险评估、外部化策略和隔离的子智能体边界（第 5、8 节）。
- **可靠执行**推动将上下文视作稀缺资源、仅追加持久状态、优雅恢复、子智能体隔离及纵深防御（第 4、7-9 节）。
- **能力放大**推动最小脚手架、可组合扩展、按可逆性加权的风险、上下文管理与优雅恢复（第 4-6 节）。
- **情境适应性**推动透明文件记忆、可组合扩展、渐进式信任谱系和外部化可编程策略（第 5-7 节）。

这些映射也揭示架构没有做什么：它不在模型推理上强加显式规划图；不提供单一统一扩展机制；恢复会话时也不会还原所有会话级、与信任相关的状态。这些缺席与上述原则一致。

### 2.4 一个贯穿全局的问题：开发者长期能力

上述五项价值描述架构被设计来服务什么。本文还追问第六个问题：架构是否帮助开发者保持长期理解和能力。这个担忧确实存在。Anthropic 对 132 名工程师和研究人员的研究（Huang et al., 2025）记录了“监督悖论”：过度依赖 AI 可能使监督 AI 所需的技能退化。独立研究（Shen and Tamkin, 2026）则发现，AI 辅助条件下的开发者在理解测试中的得分低 17%。然而，这一担忧在架构及 Anthropic 公开设计价值中并未成为显著驱动力。因此，本文不把它列为与五项价值同级的价值，而视为贯穿各处的问题：第 12 节会把它应用到全部五项价值，考察短期能力放大是否以人类长期理解、代码库一致性和开发者培养通道为代价。

## 3 架构总览

构建生产级编程智能体，需要回答一些反复出现的设计问题：推理应放在哪里，需要多少执行引擎，应采取何种安全姿态，以及把哪种资源视作硬约束。Claude Code 架构可以理解为其中一组答案。

在实现层，系统由沿主数据流连接的七个组件组成：用户通过某一界面提交提示，提示进入共享智能体循环；循环组装上下文、调用 Claude 模型、接收可能包含工具请求的响应、把请求送入权限系统，并把批准的动作分派给与执行环境交互的具体工具。在此期间，状态与持久化机制记录会话转录、管理会话身份，并支持恢复、分叉与回退。

### 3.1 设计问题与贯穿示例

本文围绕生产级编程智能体共有的四个问题组织说明；每个问题都落实表 1 中的一项或多项原则。这里先给出 Claude Code 的答案和可能替代方案，随后在第 4 至第 9 节逐步展示。

**推理位于何处？** 在 Claude Code 中，模型推理“做什么”，harness 负责执行动作。模型在响应中产生 `tool_use` 块；harness 解析、检查权限、分派给工具实现并收集结果（`query.ts`）。模型从不直接访问文件系统、运行 shell 或发起网络请求。推理与执行位于不同代码路径，这带来安全收益：即使模型遭到入侵或对抗性操控，也无法越过 harness 实施的沙箱、权限检查和默认拒绝规则。模型与外界的唯一接口是结构化 `tool_use` 协议，执行前由 harness 验证。对提取源码的社区分析估计，Claude Code 代码库约 1.6% 属于 AI 决策逻辑，其余 98.4% 是运行基础设施，显示核心推理层很薄。Devin 则维护显式规划和任务追踪结构；LangGraph 通过开发者定义的状态图路由控制流，它们在脚手架侧投入更多推理。

**需要多少执行引擎？** 无论用户通过交互终端、无头 CLI、Agent SDK 还是 IDE 集成操作，Claude Code 都使用同一个 `queryLoop()`（`query.ts`）；变化的只有渲染与用户交互层。其他系统为不同模式使用不同引擎，例如让 IDE 集成走与 CLI 不同的路径，以统一性换取针对交互表面的优化。

**默认安全姿态是什么？** Claude Code 默认采用“拒绝优先、升级给人类”：deny 规则优先于 ask，ask 又优先于 allow；未识别动作交给用户，而非静默放行（`permissions.ts`）。权限规则、`PreToolUse` 钩子、启用时的自动模式分类器和可选 shell 沙箱等独立安全层并行生效，任何一层都能阻止动作（第 5 节）。SWE-Agent、OpenHands 把信任边界转移到容器隔离；Aider 则主要依靠 Git 回滚。

**硬约束资源是什么？** 在 Claude Code 中，硬约束是上下文窗口：旧模型为 200K，Claude 4.6 系列为 1M。每次模型调用前运行五种不同的上下文缩减策略（`query.ts`）；懒加载指令、延后工具 schema 和子智能体仅返回摘要等设计也用于控制上下文消耗（第 7 节）。五层流水线存在，是因为没有单一压缩策略能处理所有压力：预算缩减处理超过尺寸上限的单个工具结果；snip 处理时间深度；microcompact 应对缓存开销；context collapse 管理极长历史；auto-compact 最后执行语义压缩。各层成本收益不同，便宜的层先于昂贵的层运行。替代架构可能把算力预算（限制模型调用或工具调用次数）或工作记忆（维护显式 scratchpad，而不是依赖对话历史）视为主要瓶颈。

**贯穿示例。** 用户从某个 Claude Code 界面提交“修复 `auth.test.ts` 中失败的测试”。随后各节将请求依次追踪到查询循环、权限门、工具池、上下文窗口、子智能体委派和会话持久化。

### 3.2 高层系统结构

七组件模型可直接映射到源码：

1. **用户：**提交提示、批准权限、审查输出。
2. **界面：**交互式 CLI、无头 CLI（`claude -p`）、Agent SDK、IDE/Desktop/Browser；所有表面汇入同一循环。
3. **智能体循环：**模型调用、工具分派和结果收集的迭代周期，由 `query.ts` 中的 `queryLoop()` 异步生成器实现。
4. **权限系统：**`permissions.ts` 的默认拒绝规则评估、自动模式 ML 分类器，以及 `types/hooks.ts` 的钩子拦截。
5. **工具：**最多 54 个内置工具，其中 19 个无条件存在，35 个取决于 feature flag 与用户类型；由 `tools.ts` 中 `assembleToolPool()` 组装，并与 MCP 工具合并。插件通过 MCP server 与技能/命令注册表间接贡献能力。
6. **状态与持久化：**以追加写入为主的 JSONL 会话转录（`sessionStorage.ts`）、全局提示历史（`history.ts`）及子智能体 sidechain 文件。
7. **执行环境：**带可选沙箱的 shell 执行（`shouldUseSandbox.ts`）、文件系统操作、网页获取、MCP server 连接与远程执行。

数据流沿从左到右的主干运行：用户通过界面提交请求，进入智能体循环；循环向权限系统提出动作；获批动作到达工具；工具与执行环境交互，将 `tool_result` 消息返回循环。状态与持久化位于循环旁，记录转录并载入既有会话数据。

`main.tsx` 中的入口 `main()` 初始化安全设置，包括防止 Windows PATH 劫持的 `NoDefaultCurrentDirectoryInExePath`，注册用于优雅退出的信号处理器，并分派到相应执行模式。

- **表面层：**交互式 CLI、无头 CLI、Agent SDK、IDE/Desktop/Browser 与 UI/renderer。
- **核心层：**智能体循环与压缩流水线。

### 3.3 分层子系统分解

**表面层（入口与渲染）。** `src/entrypoints/` 包含启动路径，SDK 入口涉及 `coreTypes.ts`、`controlSchemas.ts` 和 `coreSchemas.ts`；`src/screens/` 组合全屏布局，`src/components/` 基于 Ink 提供终端 UI 构件。交互式 CLI 启动带实时流、权限对话框和进度指示器的终端 UI。无头 CLI（`claude -p`）为单次处理创建 `QueryEngine`，它只是围绕共享查询路径的薄对话包装器（第 3.4 节）。Agent SDK 通过异步生成器发出带类型事件。

**核心层（智能体循环与压缩）。** `query.ts` 中 `queryLoop()` 异步生成器实现迭代循环：消费状态层组装的上下文，并把工具请求分派给安全/动作层。每次模型调用前，五个顺序执行的 shaper 管理上下文压力：budget reduction、snip、microcompact、context collapse 与 auto-compact（`query.ts:365-453`；第 4.3、7.3 节）。

**安全/动作层。** 权限系统（`permissions.ts`）实施默认拒绝规则评估；若计入内部 `bubble` 和 feature-gated `auto`，最多七种权限模式（`types/permissions.ts`）。集成的自动模式分类器（`yoloClassifier.ts`）采用两阶段快速过滤与思维链评估。覆盖 27 种事件的钩子流水线（`coreTypes.ts`，输出 schema 位于 `types/hooks.ts`）可以阻止、改写或注释工具请求；其中 5 种与安全相关，其余 22 种服务于生命周期与编排。插件和技能可向运行时注册工具与钩子。`assembleToolPool()` 合并内置与 MCP 工具。获批 shell 命令仍会通过独立限制文件系统和网络访问的 shell 沙箱。通过 `AgentTool`（`AgentTool.tsx`、`runAgent.ts`）生成子智能体，与其他工具一样经 `buildTool()` 分派；它以隔离上下文重新进入 `queryLoop()`，只向父智能体返回摘要（第 8 节）。

**状态层。** 上下文组装是带 memoization 的状态加载器，不是路由中心。`getSystemContext()`（`context.ts`）计算含 Git 状态的会话级系统上下文；`getUserContext()` 载入 `CLAUDE.md` 层级和当前日期。二者均被缓存：系统上下文追加到 system prompt，用户上下文则作为 user-context 消息加入。`src/state/` 管理运行状态。会话转录按项目路径存为主要只追加的 JSONL（`sessionStorage.ts`）。`CLAUDE.md` 与 memory 子系统提供从托管设置到目录级文件的四层指令层级（`claudemd.ts`），以及 Claude 在对话中写入的自动记忆。每个子智能体的对话保存在独立 sidechain 转录中（`sessionStorage.ts:247`），避免撑大父上下文。全局提示历史位于 `history.jsonl`；恢复和分叉根据转录重建状态（`conversationRecovery.ts`）。

**后端层。** 包括可选沙箱 shell 执行（`BashTool.tsx`、`PowerShellTool.tsx`）、`src/remote/` 的远程执行、支持 stdio、SSE、HTTP、WebSocket、SDK 和 IDE 适配器等传输的 MCP 连接（`services/mcp/client.ts`），以及 `src/tools/` 下 42 个实现具体工具逻辑的子目录。

### 3.4 QueryEngine：一个澄清

`QueryEngine.ts` 的类说明写道：`QueryEngine` 拥有一次对话的查询生命周期与会话状态，把 `ask()` 的核心逻辑抽取为独立类，供无头/SDK 路径以及未来的 REPL 使用。它是非交互表面的对话包装器，不是系统引擎本身。构造器接收 `QueryEngineConfig`，包括初始消息、abort controller、文件状态缓存和其他每对话状态；`submitMessage()` 是编排单轮的异步生成器。共享查询路径位于 `query.ts` 的 `query()`，内部包装 `queryLoop()`；`QueryEngine` 委派给 `query()`。

这一区分在架构上很重要：交互式 CLI 同样调用 `query()`，完全绕过 `QueryEngine`。共享代码路径是循环函数，不是引擎类。

### 3.5 权限与安全层

“默认安全”通过七个独立层实现。请求必须通过所有适用层，任一层均可阻止：

1. **工具预过滤（`tools.ts`）：**调用前从模型可见范围移除被全面拒绝的工具，使模型无法尝试调用。
2. **默认拒绝规则评估（`permissions.ts`）：**deny 永远优先于 allow，即使 allow 更具体。
3. **权限模式约束（`types/permissions.ts`）：**当前模式决定未匹配显式规则的请求如何处理。
4. **自动模式分类器：**ML 分类器评估工具安全，可能拒绝规则系统本会允许的请求。
5. **Shell 沙箱（`shouldUseSandbox.ts`）：**获批 shell 命令仍可在限制文件系统和网络的沙箱中执行。
6. **恢复时不还原权限（`conversationRecovery.ts`）：**恢复或分叉不会恢复会话级权限。
7. **钩子拦截（`types/hooks.ts`）：**`PreToolUse` 可改变权限决定；`PermissionRequest` 可与用户对话框并行异步解决决定，在 coordinator 模式下还可先于对话框。

第 5 节将详细说明这些层。

### 3.6 作为瓶颈的上下文：压缩之外

除第 7 节详述的五层压缩外，还有若干设计反映了“上下文是瓶颈”的约束：

- **`CLAUDE.md` 懒加载：**会话开始时加载基本层级；嵌套目录中的额外指令和条件规则只在智能体读取对应目录文件时加载，避免无关指令占用上下文。
- **延后工具 schema：**启用 `ToolSearch` 时，部分工具初始只提供名称，完整 schema 按需加载。
- **子智能体只返回摘要：**父智能体只接收摘要文字，不接收子智能体完整对话历史（第 8 节）。
- **单工具结果预算：**每个工具结果有可配置大小上限，避免一次冗长输出占用不成比例的上下文。

## 4 轮次执行：智能体查询循环

当用户提交“修复 `auth.test.ts` 中失败的测试”时，输入进入一个反应式循环。这只是编程智能体若干可能编排模式之一。本节考察 Claude Code 选择的简单 `while` 循环，并端到端追踪一次轮次，展示表 1 中三项原则：最小脚手架与最大运行 harness、把上下文视作稀缺资源并渐进管理、优雅恢复与韧性。

### 4.1 查询流水线

每个轮次遵循固定顺序（图 2，`query.ts`）：

1. **解析设置。** `queryLoop()` 解构系统提示、用户上下文、权限回调和模型配置等不可变参数。
2. **初始化可变状态。** 一个 `State` 对象保存跨迭代的全部可变状态，包括消息、工具上下文、压缩追踪和恢复计数器。循环的七个 `continue` 位置每次都用整对象赋值覆盖状态，而非逐字段修改。
3. **组装上下文。** `getMessagesAfterCompactBoundary()` 取得最后一个 compact boundary 之后的消息，使已压缩内容以摘要而非原消息呈现。
4. **模型调用前的上下文整形。** 五个 shaper 顺序执行（第 4.3 节）。
5. **调用模型。** `for await` 循环流式消费 `deps.callModel()`，传入组装后的消息（前置用户上下文）、完整系统提示、thinking 配置、可用工具集合、abort signal、当前模型规格，以及 fast mode、effort 和 fallback model 等选项。
6. **分派工具使用。** 若响应包含 `tool_use` 块，则进入工具编排层（第 4.2 节）。
7. **权限门。** 每项工具请求通过权限系统（第 5 节）。
8. **执行工具并收集结果。** 工具结果作为 `tool_result` 消息加入对话，循环继续。
9. **停止条件。** 响应不含 `tool_use`、仅有文本时，本轮完成。

`queryLoop()` 是一个 `AsyncGenerator`，运行期间会产生 `StreamEvent`、`RequestStartEvent`、`Message`、`TombstoneMessage` 和 `ToolUseSummaryMessage`。生成器设计让 UI 能获得流式输出，同时循环内部保持单一同步控制流。

Claude Code 的反应式循环遵循 ReAct 模式（Yao et al., 2022）：模型生成推理和工具调用，harness 执行动作，结果进入下一次迭代。替代模式包括显式图路由（LangChain, Inc., 2024）和树搜索（Zhou et al., 2023）。Anthropic 指南（Schluntz and Zhang, 2024）提出五种可组合工作流：提示链、路由、并行、orchestrator-workers、evaluator-optimizer。Claude Code 在子智能体委派中主要采用 orchestrator-workers（第 8 节），核心循环仍保持反应式。它以搜索完备性换取简单与低延迟：每轮只沿一条动作序列前进，不回溯。

### 4.2 工具分派与流式执行

模型响应包含 `tool_use` 时，系统在两条路径中选择。主路径使用 `StreamingToolExecutor`，工具块从模型响应流出时立即执行，以降低多工具响应延迟。备用路径使用 `toolOrchestration.ts` 的 `runTools()`，遍历 `partitionToolCalls()` 产生的分区。两条路径都把工具分为“并发安全”与“独占”：只读操作可并行，shell 命令等修改状态的操作串行。

`StreamingToolExecutor` 通过两项机制协调并发：

- **兄弟 abort controller：**任一 Bash 工具报错时立即终止其他执行中的子进程，而不是等待它们自然结束。
- **进度可用信号：**有新输出时唤醒 `getRemainingResults()` 消费者。

结果被缓冲，并按工具接收顺序发出，因此即使并行执行，输出顺序仍与模型请求一致。模型期待结果顺序与请求相同，这一点很重要。“并发读、串行写”介于完全串行分派和 PASTE（Sui et al., 2026）等激进推测方案之间；后者在模型仍生成时预执行预测的未来调用，用推测隐藏工具延迟。

结果收集阶段遍历流式执行器或批量 `runTools()` 异步生成器的更新。二者均由同一个 `for await` 消费；区别在于前者在模型结束流式输出前开始执行，后者先分为并发安全组再执行。更新可能携带工具结果、附件或进度事件。若附件含 `hook_stopped_continuation`，说明 `PostToolUse` 钩子要求停止继续，本轮设置 `shouldPreventContinuation`。最后由 `normalizeMessagesForAPI()` 规范化 Anthropic API 消息，仅保留 user 类型消息。

### 4.3 模型调用前的上下文整形

每次模型调用前，`query.ts` 中五个 shaper 依次操作 `messagesForQuery`。早期步骤先做轻量缩减，后期才扩大压缩范围。

1. **预算缩减（`applyToolResultBudget()`）。** 对工具结果实施逐消息大小限制，超大输出替换为内容引用；`maxResultSizeChars` 非有限值的工具例外。替换内容会持久化，以便 agent 和 session 查询源在恢复时重建。预算缩减先于 microcompact，因为后者只按 `tool_use_id` 操作、不检查内容，二者可干净组合。
2. **Snip（`snipCompactIfNeeded()`，受 `HISTORY_SNIP` 控制）。** 轻量删除较旧历史，返回 `{messages, tokensFreed, boundaryMessage}`。主 token 计数器从最近助手消息的 `usage` 推断上下文大小，而该消息在 snip 后仍携带压缩前的 `input_tokens`，所以必须显式把 `snipTokensFreed` 传给 auto-compact。
3. **Microcompact。** 始终运行基于时间的路径，并可选运行缓存感知路径（`CACHED_MICROCOMPACT`）。启用缓存路径时，boundary message 延后到 API 响应后生成，从而使用真实 `cache_deleted_input_tokens` 而非估计值。返回 `{messages, compactionInfo}`，其中可能含 `pendingCacheEdits`。
4. **Context collapse（`CONTEXT_COLLAPSE`）。** 对对话历史进行读取时投影。它不向 REPL 数组写入或删除内容；摘要存在 collapse store 中，通过 `applyCollapsesIfNeeded()` 把 `messagesForQuery` 替换为投影视图。模型看到折叠版本，完整历史仍可重建，折叠也能跨轮保留。
5. **Auto-compact。** `compact.ts` 的 `compactConversation()` 调用模型产生完整摘要。函数先执行 `PreCompact` 钩子，以 `getCompactPrompt()` 构造摘要请求，再把结果交给 `buildPostCompactMessages()`。只有前四层执行后上下文仍超过压力阈值时才触发。

### 4.4 恢复机制

查询循环处理边界情况的机制包括：

- **提升最大输出 token：**响应触及输出上限时，在 GrowthBook flag 允许且没有既有 override 或环境变量上限时，以更高限制重试；每轮最多三次（`MAX_OUTPUT_TOKENS_RECOVERY_LIMIT = 3`）。
- **反应式压缩（`REACTIVE_COMPACT`）：**接近上下文容量时，只总结到足以释放空间；`hasAttemptedReactiveCompact` 保证每轮至多触发一次。
- **提示过长：**API 返回 `prompt_too_long` 时，先尝试 context-collapse overflow recovery 和 reactive compaction；都失败后才以 `prompt_too_long` 结束。
- **流式备用路径：**`onStreamingFallback` 处理流式 API 问题，允许循环改用另一策略重试。
- **备用模型：**主模型失败时，`fallbackModel` 可切换模型。

### 4.5 停止条件

循环会因以下条件结束：模型只输出文本而不调用工具；达到可配置 `maxTurns`；API 返回 `prompt_too_long`；`PostToolUse` 钩子设置 `hook_stopped_continuation`；或 `abortController` 信号触发。

上述流水线决定工具请求如何编排与恢复。下一节研究决定请求能否执行的权限门。

## 5 工具授权与控制边界

生产级编程智能体可采用分层策略执行、操作系统级沙箱或基于版本控制的回滚。Claude Code 结合前两者，实施表 1 的四项原则：默认拒绝并升级给人类、渐进式信任谱系、分层纵深防御，以及按可逆性加权的风险评估。

当 Claude 决定调用工具，例如用 `BashTool` 运行 `npm test` 复现失败时，请求进入图 4 所示权限流水线。除 bypass 模式外，所有调用都通过权限系统。默认交互姿态下，超出只读访问的动作会请求批准；更宽松的模式以限定范围的自动批准、拒绝或分类器审查替代一部分提示。Anthropic 自动模式分析（Hughes, 2026）发现用户会批准约 93% 的权限提示，说明批准疲劳使交互确认无法独自成为可靠安全机制。系统必须在用户不警觉时仍保持安全，因此采用默认拒绝评估、全面 deny 预过滤和相互独立的沙箱层。

### 图 4：权限门与设计原则

策略核心由声明式权限规则、全局信任模式和可编程钩子组成。智能体从最小自主性开始，用户通过批准调用逐步扩展；deny 始终优先；默认与 accept-edits 模式对未知操作询问用户，可选 auto 模式把许多审查交给分类器。

### 5.1 权限模式与规则评估

类型定义中共有七种模式：

1. `plan`：模型必须先制定计划，经用户批准才执行。
2. `default`：标准交互使用，大多数操作需要用户批准。
3. `acceptEdits`：工作目录内编辑和部分文件系统命令（`mkdir`、`rmdir`、`touch`、`rm`、`mv`、`cp`、`sed`）自动批准；其他 shell 命令仍询问。
4. `auto`：ML 分类器评估未通过快速路径的请求，受 `TRANSCRIPT_CLASSIFIER` 控制。
5. `dontAsk`：不显示提示；本来需要询问的动作自动拒绝，显式 allow/deny 仍生效。
6. `bypassPermissions`：跳过大多数权限提示，但安全关键检查和不可绕过规则仍有效。
7. `bubble`：仅内部使用，让子智能体把权限请求升级到父终端。

五种外部可见模式定义在 `EXTERNAL_PERMISSION_MODES`；`auto` 只在 feature flag 有效时条件加入；`bubble` 位于类型 union，但不在模式数组中。

规则按 deny-first 顺序评估（`permissions.ts`）。`toolMatchesRule()` 先检查 deny；deny 永远优先于 allow，即使 allow 更具体。因此“拒绝全部 shell 命令”不能被“允许 `npm test`”覆盖。规则既支持按工具名匹配，也支持按输入内容匹配，如 `Bash(prefix:npm)`。

七种模式构成从 `plan`、`default`、`acceptEdits` 到 `bypassPermissions` 的渐进自主谱系。自主性越高，系统越需要从交互批准转向自动安全检查。SWE-Agent 与 OpenHands 用 Docker 隔离整个执行环境；Aider 依靠 Git 让修改可逆。Claude Code 在可选容器沙箱之上叠加多种逐操作策略机制，以更高复杂性换取细粒度控制。

### 5.2 授权流水线

完整授权经过若干阶段：

**预过滤。** 组装工具池时，`filterToolsByDenyRules()` 从模型视野中完全移除 blanket-denied 工具。它与运行时权限检查使用同一 matcher，因此 `mcp__server` 之类 server-prefix 规则能在模型看到前移除该 server 的所有工具，避免浪费调用。

**`PreToolUse` 钩子。** 钩子可返回 `permissionDecision`（deny 或 ask）或用 `updatedInput` 修改参数。钩子返回 allow 不会越过后续 deny 或安全检查。交互路径先排队用户对话框，再异步运行钩子；coordinator 与类似后台路径先等待自动检查，必要时才显示对话框。

**规则评估。** 默认拒绝引擎评估请求。MCP 工具用完整 `mcp__server__tool` 名匹配，server 级规则匹配其全部工具。

**权限处理器。** `useCanUseTool.tsx` 根据运行上下文分成四条路径：

1. `Coordinator`：多智能体协调模式，先尝试分类器、钩子和规则等自动解决，再退回用户交互。
2. `Swarm worker`：为多智能体 swarm 中的 worker 提供单独解决逻辑。
3. `Speculative classifier`：启用 `BASH_CLASSIFIER` 且工具为 Bash 时，让提前启动的分类结果与超时竞速；高置信结果立即批准。
4. `Interactive`：后备路径，通过终端 UI 显示标准审批对话框。

分类器或 deny 规则阻止动作时，系统把拒绝当作路由信号而不是硬停止：模型收到理由，调整方案，并在下一轮尝试更安全的替代动作。`PermissionDenied` 钩子允许外部代码观察并以程序方式响应拒绝。权限执行由此塑造智能体行为，而不只是终止它。

### 5.3 自动模式分类器与钩子生命周期

启用时，`yoloClassifier.ts` 的自动模式分类器参与权限决策，并加载基础系统提示、外部权限模板和 Anthropic 内部用户专用模板。它根据对话转录与权限模板评估工具调用，输出 allow、deny 或手动审批。`isUsingExternalPermissions()` 根据 `USER_TYPE` 和 `forceExternalPermissions` 选择模板。

源码定义的 27 个钩子事件中，有 5 个直接进入权限流，并具有 Zod 验证的输出 schema：

- `PreToolUse`：返回 deny/ask、理由，并可修改输入；allow 不绕过后续检查。
- `PostToolUse`：注入 `additionalContext`；对 MCP 工具还可用 `updatedMCPToolOutput` 修改进入上下文前的结果。
- `PostToolUseFailure`：为错误注入指导上下文。
- `PermissionDenied`：在自动模式拒绝后给出重试指导。
- `PermissionRequest`：返回 allow/deny；在 coordinator 等路径可先于用户对话框解决，标准交互路径可与对话框并行。

非 MCP 工具会先发出 `tool_result` 再运行 `PostToolUse`；MCP 工具的结果延后到 post hook 完成后，因此修改可生效。

### 5.4 Shell 沙箱

`shouldUseSandbox.ts` 为 Bash 与 PowerShell 提供额外保护。`shouldUseSandbox()` 检查全局开关、调用是否选择退出，以及命令是否匹配排除模式。启用后，沙箱在应用层权限模型之外独立提供文件系统与网络隔离。获批命令仍可被沙箱限制；被拒命令则根本不会到达沙箱。两者分别处理授权与隔离。

分层安全假设各层相互独立，一层失败会由其他层兜底。但多层可能共享性能约束。安全研究者（Adversa.ai, 2026）记录：包含超过 50 个子命令的命令会退化为一次通用批准，而不再逐子命令检查 deny，因为解析曾导致 UI 卡死。这说明共享故障模式会削弱纵深防御，是第 12.3 节进一步讨论的安全-性能张力。

³ 独立研究还报告了分析版本中的网络限制 parser differential：host allowlist 用 JavaScript suffix match，而域名解析在嵌入 null byte 处截断，构造 hostname 可通过后缀检查却解析到被阻止主机。报告影响 v2.0.24-v2.1.89，包括本文 v2.1.88；未分配 CVE（Cyber Security News, 2026，Tier C）。

## 6 可扩展性：MCP、插件、技能与钩子

编程智能体需要决定扩展表面是统一机制、少数专用机制，还是上下文成本不同的分层栈。本节体现两项原则：可组合的多机制扩展，以及外部化可编程策略。在例子中，Claude 已通过权限系统处理 `npm test`，接下来要决定修复 `auth.test.ts` 时可使用哪些扩展动作。

一个轮次开始时，模型不只看到 `BashTool`、`FileReadTool` 等内置工具，还可能看到 MCP server 的数据库查询工具、`.claude/skills/` 下自定义 lint 技能，以及已安装插件贡献的工具。四种机制插入循环的不同位置：MCP 提供外部工具集成；插件打包分发组件；技能注入领域指令；钩子拦截工具执行生命周期。`CLAUDE.md` 和子智能体分别属于上下文构造与委派子系统，因此另节讨论；但这些机制的上下文成本顺序具有架构意义。

### 图 5：扩展机制插入智能体循环的位置

每个循环有三个注入点：`assemble()` 控制模型看见什么；`model()` 控制模型能触达什么；`execute()` 控制动作是否以及如何执行。`CLAUDE.md`、skill 描述、MCP resource/prompt、output style 和部分钩子影响组装；内置工具、MCP 工具、`SkillTool` 与 `AgentTool` 进入模型工具池；权限规则和执行前后钩子控制动作。

### 6.1 四种扩展机制

**MCP server。** Model Context Protocol 是主要外部工具集成路径。server 从 project、user、local、enterprise 等 scope 配置，运行时再合并插件和 `claude.ai` server（`services/mcp/config.ts`）。客户端支持 stdio、SSE、HTTP、WebSocket、SDK、IDE 专用 `sse-ide`/`ws-ide` 及内部 `claudeai-proxy`。每个连接 server 贡献 `MCPTool`；内置 `ListMcpResourcesTool`、`ReadMcpResourceTool` 访问 MCP resource。

**插件。** 插件既是打包格式，也是分发机制。`PluginManifestSchema` 接受十类组件：commands、agents、skills、hooks、MCP servers、LSP servers、output styles、channels、settings、user configuration。loader 验证 manifest 并路由到相应 registry：command/skill 通过 `SkillTool` 暴露；agent 进入 `AgentTool` 定义；hook 合入 registry；MCP/LSP 合入标准配置；output style 修改响应格式。一个包可同时扩展多类组件，因此插件是第三方扩展的主要分发载体。

**技能。** 每项技能由带 YAML frontmatter 的 `SKILL.md` 定义。`parseSkillFrontmatterFields()` 解析显示名、描述、允许工具、参数提示、模型 override、`fork` 隔离执行、关联 agent、effort、shell 配置等 15 个以上字段。技能可定义调用时动态注册的钩子；内置技能在启动时内存注册。调用后，`SkillTool` 把完整指令注入上下文。

**钩子。** 源码定义 27 种事件，涵盖工具授权、会话生命周期、用户交互、子智能体协调、上下文管理、工作区事件与通知。其中 15 种具有事件专用输出 schema，可支持权限决定、上下文注入、输入修改、MCP 结果变换和重试。持久钩子命令有四类：shell command、LLM prompt、HTTP 和 agentic verifier；SDK 与内部 instrumentation 还支持不可持久化 callback。启动时从 `settings.json`、插件和 managed policy 加载；skill hook 在调用时注册。

### 6.2 工具池组装

`tools.ts` 把 `assembleToolPool()` 称为“合并内置工具与 MCP 工具的唯一真相来源”。它执行五步：

1. **枚举基础工具。** `getAllBaseTools()` 最多返回 54 个工具：19 个始终加入，35 个依 feature flag、环境变量与用户类型条件加入。内部用户获得额外工具；worktree 模式启用进入/退出工具；agent swarm 启用 team 工具；Bun 二进制含内嵌搜索时省略专用 Glob/Grep。
2. **按模式过滤。** `CLAUDE_CODE_SIMPLE` 下仅保留 Bash、Read、Edit（REPL 分支为 `REPLTool`，必要时加 coordinator 工具）；每个工具还调用 `isEnabled()` 检查运行可用性。
3. **Deny 预过滤。** 在模型看到前移除 blanket-denied 工具。
4. **整合 MCP。** 过滤 `appState.mcp.tools` 后与内置工具合并。
5. **去重。** 按名称去重；内置工具优先于 MCP 同名工具。

REPL 与 `AgentTool` 构建 worker 工具集合时都调用此函数，保证路径一致。请求时，延后工具可保持隐藏，直到通过 `ToolSearch` 明确查询。`.claude/agents/*.md` 与插件贡献的自定义 agent 因创建全新隔离上下文，不属于扩展当前上下文的四机制，放在第 8 节讨论。

### 6.3 为什么是四种机制？

每多一种机制都会增加开发者学习面积，Claude Code 却没有合并为一两种。原因是不同扩展对上下文窗口的成本不同；单一机制无法同时覆盖零上下文生命周期钩子和 schema 庞大的工具 server，而不迫使作者承担无谓权衡。

### 表 2：各扩展机制的独有能力

| 机制 | 独有能力 | 上下文成本 | 插入点 |
|---|---|---|---|
| MCP server | 多传输外部服务集成 | 高（工具 schema） | `model()`：工具池 |
| 插件 | 多组件打包与分发 | 中（视组件而定） | 三个点全部 |
| 技能 | 领域指令与 meta-tool 调用 | 低（仅描述） | `assemble()`：上下文注入 |
| 钩子 | 生命周期拦截与事件自动化 | 默认零 | `execute()`：工具前后 |

MCP 以 server 管理开销和 schema 上下文为代价，赋予模型新工具；技能以极低成本塑造智能体如何思考，因为提示中常驻的只有 frontmatter 描述；钩子默认不占上下文即可进行跨生命周期控制，也可主动注入额外上下文；插件把其他机制任意组合为可分发包，本身不是新的运行原语。成本从 hooks 的零、skills 的低、plugins 的中到 MCP 的高，使廉价扩展可以广泛扩展而不耗尽上下文，昂贵扩展则保留给确需新工具表面的情形。代价是开发者更难判断某项集成应使用哪种机制。

## 7 上下文构造与记忆

如何管理上下文窗口并持久保存用户指令，是智能体的核心设计选择。系统可能选择透明文件、数据库检索或不透明学习表示。Claude Code 在这里实施两项原则：将上下文视作稀缺资源并渐进管理，以及透明、基于文件的配置与记忆。

此时例子已经积累了原始请求、`npm test` 权限结果、第 6 节组装的工具池，以及文件读取与命令输出。本节研究在下一次模型调用前，如何把这些状态装入有限窗口。

### 图 6：上下文构造与记忆层级

来源包括系统提示、output style、环境信息、`CLAUDE.md` 层级、auto memory、路径规则、MCP 工具名、经 `ToolSearch` 延迟载入的定义、对话历史、文件读取、命令输出、工具结果、子智能体摘要与 compact summary。系统/项目配置/记忆在启动时加载；对话与运行结果逐轮积累；延后工具按需加载。执行期间可变性逐渐提高。

### 7.1 上下文窗口组装

上下文由以下来源组成：

1. 系统提示，包括 output style 修改和 `--append-system-prompt`。
2. `getSystemContext()` 提供的环境信息：Git 状态（远程模式或禁用 Git 指令时跳过）和内部构建可选 cache-breaking 注入；每会话 memoize 一次。
3. `getUserContext()` 载入的四层 `CLAUDE.md` 指令；同样 memoize。
4. 路径规则：智能体读取匹配目录文件时懒加载。
5. Auto memory：异步预取与当前情境相关的条目。
6. 工具 metadata：skill 描述、MCP 工具名及按需完整定义。
7. 受压缩控制的对话历史。
8. 文件读取、命令输出和子智能体摘要等工具结果。
9. 替换较旧历史区段的 compact summary。

`query.ts` 用 `asSystemPrompt(appendSystemContext(systemPrompt, systemContext))()` 合并系统上下文与基础提示；用户上下文通过 `prependUserContext()` 前置到消息数组。因此 `CLAUDE.md` 在 API 请求中的结构位置不同于系统提示，可能影响模型注意模式。

部分来源在主窗口构造后才注入：相关记忆预取、MCP 指令增量、agent listing 增量和后台 agent 任务通知。因此窗口在轮次中仍可增长。

### 7.2 `CLAUDE.md` 层级与自动记忆

记忆系统遵循一项原则：存储的上下文应当可由用户检查与编辑。`CLAUDE.md` 是纯 Markdown，而不是结构化配置或不透明数据库。它牺牲部分表达能力来换取可审计性；项目记忆还可与代码一起版本控制。基于 embedding 的检索更灵活，却让用户难以查看或修改“系统认为什么相关”；数据库记忆可结构化查询，却需要额外设施且不适合版本控制。

Claude Code 不使用 embedding 或向量相似度索引检索记忆，而以 LLM 扫描记忆文件 header，按需选择最多五个相关文件；检索粒度是文件，不是条目。Embedding 系统可更精细地检索单条信息，但代价是可检查性和索引维护设施。

源码定义四类 memory：

1. **Managed memory：**如 Linux 的 `/etc/claude-code/CLAUDE.md`，面向所有用户的 OS 级策略。
2. **User memory：**`~/.claude/CLAUDE.md`，私有全局指令。
3. **Project memory：**项目根中的 `CLAUDE.md`、`.claude/CLAUDE.md` 与 `.claude/rules/*.md`，随代码提交。
4. **Local memory：**项目根中的 `CLAUDE.local.md`，被 Git 忽略，用于私有项目指令。

发现过程从当前目录向根遍历，检查每层项目与本地文件；越接近当前目录优先级越高，并更晚加载，以获得更多模型注意。根到 CWD 路径中 `.claude/rules/*.md` 的无条件规则在启动时急切加载；CWD 以下嵌套目录中的规则即使无条件，也要等智能体读取匹配目录文件时懒加载。因此模型指令会随代码探索而演化。

`CLAUDE.md` 作为 user message 而非 system prompt 传递，所以遵从是概率性的，不是确定保证。按 deny-first 评估的权限规则提供确定执行层，形成“指导（概率性）”与“执行（确定性）”的有意分离。加载内容还通过 `setCachedClaudeMdContent()` 缓存给自动模式分类器，以避免 loader 与权限系统之间的 import cycle。

记忆文件支持 `@include` 模块化指令，形式包括 `@path`、`@./relative`、`@~/home` 和 `@/absolute`，仅在叶文本节点生效，不在代码块生效。实现先压入包含文件，再追加被包含文件；通过已处理路径避免循环；不存在的文件静默忽略。

### 7.3 压缩流水线

五层流水线以渐进压缩落实“上下文是瓶颈”：先应用破坏最小的压缩，廉价策略不足时才升级。预算缩减始终生效，snip、microcompact、context collapse 受 flag 控制，auto-compact 默认启用但可关闭：

1. Budget reduction：逐工具结果大小限制。
2. Snip（`HISTORY_SNIP`）：轻量删除较旧历史。
3. Microcompact（`CACHED_MICROCOMPACT`）：细粒度、缓存感知压缩。
4. Context collapse（`CONTEXT_COLLAPSE`）：对历史的读取时虚拟投影。
5. Auto-compact：模型生成完整摘要。

复杂性是其代价：五层相互作用且多层由 flag 控制，用户很难完全预测。Auto-compact 在转录中生成可见摘要，microcompact 发出边界标记，context collapse 却没有用户可见输出。单次截断更损失信息，但更容易推理。

`buildPostCompactMessages()` 返回 `[boundaryMarker, ...summaryMessages, ...messagesToKeep, ...attachments, ...hookResults]`。边界通过 `annotateBoundaryWithPreservedSegment()` 记录 `headUuid`、`anchorUuid`、`tailUuid`，支持读取时链修补。压缩不会修改或删除已写入的转录行，只追加边界与摘要事件。

`compactConversation()` 先触发 pre-compact hooks，允许注入自定义指令。GrowthBook flag 决定压缩是否复用主对话 prompt cache；源码注释记录 2026 年 1 月实验：“false 路径 98% cache miss，约占全体 `cache_creation` 的 0.76%”。压缩后，attachment builder 从实时应用状态重新声明计划、技能和异步 agent，因为压缩会丢弃旧附件消息，但不会丢弃底层状态。

当系统把工作委派给各自拥有有限窗口的子智能体时，上下文隔离会变得更加关键。

## 8 子智能体委派与编排

多智能体编排是编程智能体的重要设计维度，可采用父子层级、基于同伴对话的框架（Wu et al., 2024）或图结构工作流引擎（LangChain, Inc., 2024）。Claude Code 实施表 1 的“隔离子智能体边界”，并结合默认拒绝的人类升级和按可逆性加权的工具限制。

若 Claude 判断修复认证测试前应先探索认证模块结构，它可把探索委派给子智能体。委派机制是 `Agent` 工具（`AgentTool.tsx`），`Task` 保留为旧别名。模型传入结构化输入：委派提示、可选子智能体类型，以及隔离模式、权限 override 和工作目录配置。

### 8.1 Agent 工具与委派标准

`Agent` 输入 schema 使用 feature-gated 字段；底层能力关闭时，相应可选参数也不出现。`isolation` 对内部用户提供 `worktree`、`remote`，外部用户只有 `worktree`；`cwd` 受 feature flag 控制；背景任务关闭或 fork-subagent 模式启用时，省略 `run_in_background`。

依 feature flag 和入口不同，最多有六种内置子智能体：

- **Explore：**以读取/搜索为主，deny-list 中包含写入与编辑工具。
- **Plan：**创建结构化计划，执行仍通过标准权限模型。
- **General-purpose：**广泛能力；仅在明确请求时使用。省略类型可能转到 fork-subagent 路径，该路径复用父对话上下文而非隔离。
- **Claude Code Guide：**入门与文档辅助，有自己的 `permissionMode` override。
- **Verification：**运行测试套件、lint 等验证。
- **Statusline-setup：**配置终端状态栏。

用户可用 `.claude/agents/*.md` 定义自定义子智能体，插件也可通过 `loadPluginAgents.ts` 提供定义。Markdown 正文作为 system prompt；YAML frontmatter 可设置 description、工具 allowlist、`disallowedTools`、模型、effort、`permissionMode`、MCP server、hooks、`maxTurns`、skills、memory scope、background 和 isolation。JSON 定义支持同样字段，并以 `prompt` 显式提供提示。因此，自定义 agent 可以成为拥有独立工具、模型、权限、钩子、记忆范围和隔离方式的完整子系统。

`AgentTool` 与 `SkillTool` 都是基础工具池的 meta-tool，但本质不同：`SkillTool` 通常把指令注入当前窗口，也可选择 `context: fork`，通过同一 `runAgent()` 机制创建隔离子智能体；`AgentTool` 始终创建新的隔离实例。代价是大多数子智能体调用需要自包含提示，因为默认路径不继承父历史，fork-subagent 例外。共享完整历史的对话框架没有这项提示成本，却可能随 agent 数量产生上下文爆炸。

### 图 7：子智能体隔离与委派架构

`Agent` 分派到 Explore、Plan、general-purpose 或 custom agent。每个实例使用隔离上下文、重建的权限上下文和独立工具集合，并可沿三个轴配置：路由（teammate）、隔离（remote/worktree）、生命周期（async/sync）。子智能体写独立转录，只将报告与 metadata 插回主对话。

### 8.2 隔离架构

支持三种模式：

- **Worktree：**创建临时 Git worktree，让子智能体修改自己的仓库副本，不影响父工作树。
- **Remote（仅内部）：**在远程 Claude Code Remote 环境启动，始终后台运行。
- **In-process（默认）：**共享父文件系统，但使用隔离对话上下文。

权限 override 有明确优先级。子智能体定义 `permissionMode` 时通常应用，但父会话若处于 `bypassPermissions`、`acceptEdits` 或 `auto`，则父模式优先，因为它代表用户已经明确选择安全/自主权衡。异步 agent 是否显示提示按级联决定：先看显式 `canShowPermissionPrompts`；再看 `bubble`（总显示，因为升级到父终端）；最后默认同步 agent 显示、异步不显示。允许显示提示的后台 agent 设置 `awaitAutomatedChecksBeforeDialog: true`，先让分类器与钩子解决，再中断用户。

这些模式位于不同设计点：容器隔离有更强资源边界但需要容器基础设施；AutoGen 等只隔离对话、共享文件系统；Claude Code 用 Git worktree 获得工作区级文件分离而无需容器编排。

若 `runAgent()` 显式收到 `allowedTools`，则使用两级权限范围：SDK 的 `--allowedTools` 被保留并适用于所有 agent；会话级规则被子智能体声明的 allowlist 替换。未提供时（常见 `AgentTool` 路径），继承父会话规则。

### 8.3 Sidechain 转录

每个子智能体把转录写入独立 `.jsonl`，并配套 `.meta.json`（`sessionStorage.ts`、`runAgent.ts`）。历史因此可用于调试审计，却不撑大父会话文件。父上下文只接收最终响应文字和 metadata，完整子历史从不进入父窗口。

“仅摘要返回”是有意的上下文节约。共享完整历史会随 agent 数量产生爆炸；即使隔离并行也成本高。Claude Code Agent Teams 在 plan mode 中约消耗标准会话 7 倍 token（Anthropic, 2025b），因此多个隔离上下文并存时，摘要返回尤其重要。

Agent Teams 的多实例协调使用文件锁，而不是消息 broker 或分布式协调服务。每个 teammate 有独立 inbox JSON（`utils/teammateMailbox.ts`）；任务和消息在逐 inbox lockfile 下写入可预测路径。它用吞吐量换取零依赖部署和完全可调试：读取纯 JSON 即可检查任一 agent 状态。

## 9 会话持久化与恢复

会话持久化可采用仅追加日志、结构化数据库、检查点快照或无状态架构，各自在可审计性、查询能力和部署复杂度上权衡。Claude Code 实施“仅追加持久状态”。会话级权限只存在内存，不序列化到转录；恢复时从 CLI 参数和磁盘设置重建权限上下文，未识别请求回到 deny-first 提示。

此时认证测试会话包含原提示、工具调用与结果、compact boundary，以及探索模块的子智能体摘要。本节研究哪些工件被持久记录，以及哪些能在不继承旧权限的情况下恢复。

### 图 8：会话持久化与上下文压缩

图中把实时会话状态（窗口、压缩）与持久存储（session transcript、`history.jsonl`、subagent sidechain、文件检查点）分开。转录让对话寿命超出窗口容量；append-only 结构让用户能 rewind、resume 或 fork 到新路径。恢复和分叉还原消息，但不还原会话级权限。

### 9.1 转录模型

转录以项目为单位存入主要只追加的 JSONL；显式清理重写是例外。`getTranscriptPath()` 计算 `join(projectDir, ${getSessionId()}.jsonl)`；`projectDir` 先取恢复/分支时 `switchSession()` 设置的 `getSessionProjectDir()`，否则取原始 CWD 对应项目目录。

三个通道独立运行：

1. **Session transcript：**用户、助手、附件和系统消息，以及压缩和 metadata 事件；每项目每会话一文件。
2. **全局提示历史：**仅用户提示，位于配置 home 的 `history.jsonl`。`makeHistoryReader()` 经 `readLinesReverse()` 倒序产出，支持上箭头和 `Ctrl+R`。
3. **Subagent sidechain：**每个子智能体独立 `.jsonl + .meta.json`。

转录还记录 compact marker、file-history snapshot、attribution snapshot 和 content replacement。Append-only JSONL 偏向可审计性和简单性，而非查询能力：事件人类可读、可版本控制，无需专用工具检查。数据库能提供更丰富查询，却引入部署依赖并降低透明度。

会话身份把 `sessionId` 与 `sessionProjectDir` 配对，在 resume/branch 时共同设置。转录路径必须使用写消息时的同一项目目录，避免 hook 查错位置。

### 9.2 恢复、分叉与“不恢复权限”

`--resume` 通过重放转录重建对话；fork 从既有会话创建新会话。但二者都不还原会话级权限，用户必须重新授权。这是保守的安全选择：会话被视作隔离信任域。自动继承旧授权虽方便，却可能把陈旧信任决定带入已变化的上下文；架构接受用户摩擦，以维持“信任总在当前会话建立”的不变量。

`compact_boundary` 为持久化而设计。`annotateBoundaryWithPreservedSegment()` 在边界事件记录 `headUuid`、`anchorUuid`、`tailUuid`；loader 在读取时据此修补消息链，保留消息在磁盘上的原 `parentUuid`。压缩通常无需修改或删除旧行。

Claude Code 的“checkpoints”是 `--rewind-files` 使用的文件历史快照，位于 `~/.claude/file-history/<sessionId>/`；它不是通用检查点存储。

## 10 比较分析：Claude Code、OpenClaw 与 Hermes Agent

前文记录了 Claude Code 对循环、安全、扩展、上下文、委派和持久化问题的回答。本节把它与两个起点完全不同的开源系统比较，以放入更广的智能体设计空间。

OpenClaw 是 local-first WebSocket gateway，把 WhatsApp、Telegram、Slack、Discord、Signal 等消息表面连接到嵌入式 agent runtime，并有 macOS/iOS/Android companion app。Hermes Agent 是单个 Python 进程，其角色由启动入口决定；一个持久化层和多个交互表面共同面对同一运行时。Hermes 有三个 console script：`hermes` 用于 CLI 与 gateway controller，`hermes-agent` 用于 batch，`hermes-acp` 是 Agent Client Protocol 适配器，让外部 IDE 可像 Hermes gateway 托管其他 agent 一样托管 Hermes。

Claude Code 是绑定单仓库会话的 CLI coding harness；OpenClaw 是多通道个人助理的持久控制平面；Hermes 是由入口决定角色和表面的单进程。比较的价值在于说明部署情境变化后，同一问题会产生何种不同答案。

⁴ 源码检查发现 Hermes 文档与实现有两处漂移：`SECURITY.md` 写审批模式为 `on/auto/off`，而 `tools/approval.py:721-750` 返回 `manual/smart/off`；文档写委派默认深度为 2，而 `delegate_tool.py:128` 设置 `MAX_DEPTH = 1`。本文采用源码。

### 10.1 六个比较维度

### 表 3：三套系统的架构比较

| 维度 | Claude Code | OpenClaw | Hermes Agent |
|---|---|---|---|
| 系统范围 | CLI/IDE 编程 harness；每会话临时进程 | 持久 WS gateway daemon；多通道控制平面 | 单 Python 进程，角色由 `hermes`/`hermes-agent`/`hermes-acp` 入口决定；内置及插件消息表面；`state.db`、`kanban.db` 两个 SQLite 文件 |

三者还可组合：OpenClaw 可经 ACP 托管 Claude Code、Codex 和 Gemini CLI；Hermes 同时位于 ACP host/guest 两侧，其 gateway 托管平台适配器与 tool server，`hermes-acp` 又允许外部 IDE 托管 Hermes。因此它们可层叠，不只是替代品。

**系统范围与部署模型。** Claude Code 是绑定仓库的临时 CLI。OpenClaw 是持久 daemon（默认 `127.0.0.1:18789`），拥有全部消息表面连接，通过带类型 WS 协调 client、tool 与 device node。Hermes 是由入口固定角色的长期 Python 进程；gateway 子命令通过内置 `gateway/platforms/` 和 `plugins/platforms/` 两级 adapter 驱动渠道，并以两个 SQLite 文件保存 session 与 board 状态，不设 broker。Hermes 的信任拓扑更像 OpenClaw，进程拓扑更像 Claude Code。系统范围是最根本差异，它决定其他问题如何被提出。

**信任与安全。** Claude Code 假定“不可信模型运行在可信开发者机器”，逐调用权限、ML classifier 与七种模式构成自主谱系。OpenClaw 假定每个 gateway 有一个可信 operator，先做身份访问控制而非逐动作分类；工具按 agent 配 allow/deny，可选沙箱默认不启用，且不把共享 gateway 的敌对多租户隔离视作受支持边界。Hermes 居中：`HARDLINE_PATTERNS` 无条件阻止 `rm -rf /`、`mkfs`、对块设备原始 `dd`、fork bomb 和关机；smart 模式用辅助 LLM 风险评估。它像 Claude Code 逐操作审批，却像 OpenClaw 在多表面渲染。三者信任边界分别位于模型与执行环境之间、gateway 周界、两者之间。

**运行时与工具编排。** Claude Code 的异步循环直接管理上下文、模型、工具与恢复。OpenClaw 的 loop 是较大 gateway dispatch 中的组件；RPC 验证参数并解析 session 后立即返回，嵌入 runner 执行循环并回传事件，逐 session queue 与可选全局 lane 防止跨渠道竞争。Hermes 用同步 Python while、线程管理并发和工具自注册；多工具调用并行，失败时串行回退。三者都遵循 ReAct，但 loop 在架构中的位置不同。

**扩展架构。** Claude Code 扩展单 agent 的动作表面；OpenClaw plugin 扩展 gateway 中所有 agent 共享的能力表面，并有 ClawHub 与 MCP；Hermes 在类似 Claude Code 的逐 agent 表面之外，增加整套 memory/model backend 替换轴。Hermes 启动 stdio MCP server 前只传递少量系统环境变量，并用 OSV 恶意软件库筛查 `npx`/`uvx` 包名。

**记忆、上下文与知识管理。** 三者都偏好用户可见、可编辑文件。Claude Code 投资于五层、缓存感知压缩；OpenClaw 投资于长期记忆晋升：`MEMORY.md`、按日期笔记、可选 `DREAMS.md`、hybrid retrieval 和后台 consolidation，并在压缩前提醒 agent 保存重要笔记；Hermes 投资于注入前内容扫描和在提示层把持久记忆与压缩历史隔离。Hermes 会检测注入模式和不可见 Unicode，命中时用 `[BLOCKED: ...]` 代替文件内容。

**多智能体架构与路由。** Claude Code 是父 agent 创建从属 worker；OpenClaw 把“多 agent 路由”与“单 agent 内子任务委派”分开，前者可为不同用户/目的创建真正独立实例；Hermes 又在另一处切分：`delegate_task` 做逐轮委派，SQLite Kanban 则提供持久共享任务板。Hermes child 默认禁用持久记忆，不能读写父笔记；Kanban 会回收过期领取，并在连续两次失败后自动阻止任务。

### 10.2 比较表之外的 Hermes 能力

Hermes 用 WAL 模式 SQLite 保存全部 session 消息并提供全文检索，以 parent-session chain 记录压缩触发的分裂。相比 Claude Code 逐项目 JSONL，它原生支持跨会话搜索与并发读者。Gateway 在对话中途重启后，下一条消息到达时可按 transcript timestamp 新鲜度自动恢复，默认窗口一小时。

内置 cron 与 webhook 让 agent 按计划表达式或外部 HTTP 事件无人值守运行；cron session 禁用持久记忆，默认 inactivity timeout 为 600 秒。后台 curator 会审查 agent 创建的 skills、归档陈旧项但不删除；仅处理来源为 agent 的 skill，不碰 bundled 或 hub 安装内容。这些能力来自 Hermes 的持久进程范围，Claude Code 的逐会话 CLI 模式不提供同样属性。

### 10.3 对照揭示了什么

比较得出三点。

第一，第 3.1 节的问题并不局限于编程智能体。OpenClaw 从多通道个人助理出发回答，Hermes 从单进程多表面出发回答；问题稳定，答案随部署情境变化。

第二，三者押注不同。Claude Code 投资渐进逐操作安全；OpenClaw 投资周界身份与访问控制；Hermes 位于中间。Claude Code 把 loop 作为中心；OpenClaw 把 gateway 控制平面作为中心；Hermes loop 在运行时层与 Claude Code 平级。Claude Code 扩展单个窗口，OpenClaw 扩展共享 gateway，Hermes 还可整体替换记忆和模型后端。这些差异来自不同信任模型和部署拓扑，并非任意。

第三，组合关系很重要。OpenClaw 可把 Claude Code 作为外部 coding harness；Hermes 既可托管平台 adapter/tool server，又可被外部 IDE 托管。AI 智能体设计空间不是扁平分类，而是分层结构：gateway 级系统与任务级 harness 可以在多个位置组合。

| 行内补全 | Copilot、Tabnine | 编辑器插件 |
| 聊天集成 | Cursor、Windsurf、Cody | 与 IDE 耦合的产品 |
| 智能体 CLI | Claude Code、Codex CLI、Aider | 工具使用循环 |
| 完全自主 | Devin、SWE-Agent、OpenHands | 沙箱 + 规划 |

行内补全只在编辑器建议代码片段；聊天集成增加多文件编辑但仍绑定 IDE；智能体 CLI 可在一次请求内自主运行 shell、读写文件并迭代；完全自主系统力求在云沙箱中以最少监督工作。Claude Code 具有自动分类器、后台 agent、远程环境等高自主功能，但默认仍交互审批。SWE-Bench、HumanEval 等 benchmark 推动了大量学术研究，本文则从源码考察内部架构。

### 11.2 智能体架构模式

Claude Code 核心遵循 ReAct：模型推理并调用工具，harness 执行动作，结果进入下一轮。Toolformer（Schick et al., 2023）证明语言模型可学习使用工具。Weng（2023）提出规划、记忆、工具使用的经典拆分；Wang et al.（2024a）梳理早期自主智能体；Xu（2026）以自主性/可控性、延迟/准确性、能力/可靠性三组权衡组织领域；Hu et al.（2024）则把 agent 设计本身视作对组件、算法和评估函数的搜索。本文描述这一空间中的一个具体点。

“代码作为 agent harness”的近期综述（Ning et al., 2026）不仅把代码视作模型输出，也视作推理、行动、环境建模和基于执行验证的基底，这与本文关注模型外围 harness 一致。AutoGen、LangChain、CrewAI 等提供基于对话的多 agent 协调；Claude Code 则增加权限 override 优先级、两级权限范围和逐 agent 转录。LATS 以树搜索统一推理、行动和规划；Claude Code 的 plan mode 是更简单的先规划后执行。

实践文章逐渐收敛到若干模式。Anthropic 的 “Building Effective Agents” 主张简单可组合模式胜过重框架。Martin（2026）总结生产系统七种模式，包括把文件系统和 shell 作为通用动作层、按需发现动作而非预载全部 schema。Chase（2025）称 Claude Code 的规划工具“基本是 no-op”，价值在于让 agent 不偏离任务。Wang（2025）认为学术框架最常漏掉的是 authority。Huyen（2025）用复合错误说明：单步 95% 准确率下，100 步任务整体成功率仅 0.6%，因此需要逐步验证。OpenAI 也把 harness 设计本身视作核心工程任务。

近期还出现 loop engineering：开发者不逐轮提示，而构建寻找工作、分派、检查结果、决定下一步的循环，由 skills、MCP 和 subagents 等原语组合（Osmani, 2026）。它允许单个开发者引导更多自主工作，但减少逐轮参与也加剧长期能力问题。

**上下文管理。**

### 表 5：LLM 工具的上下文管理设计空间

| 方法 | 机制 | 粒度 |
|---|---|---|
| 简单截断 | 删除最旧消息 | 粗 |
| 滑动窗口 | 固定大小近期历史 | 中 |
| RAG | 检索相关片段 | 细 |
| 单次摘要 | 一次压缩 | 粗 |
| 渐进压缩 | 多层流水线 | 很细 |

Claude Code 在升级前以不同粒度应用多种策略，包含缓存感知和读取时虚拟视图。Zhang et al.（2025a）指出摘要会丢领域细节，反复改写上下文还会逐步损失信息，因此提出把上下文作为不断积累策略的“演化 playbook”。`CLAUDE.md` 积累结构化指令而非反复摘要，与此一致。Hu et al.（2025）区分临时组装的 context engineering 与持久事实/经验记忆，Claude Code 也以压缩流水线配合文件记忆层级。

**安全与权限。** 安全架构沿三轴变化：审批模型（逐操作、分类器自动化、无提示事后审查）；隔离边界（容器、文件沙箱、按权限限定工具池或无隔离）；恢复机制（Git 回滚、会话权限重置、checkpoint rewind）。Claude Code 同时使用 deny-first、ML 审批、可选 shell 沙箱和不跨会话恢复权限。Windows sandbox 和云 agent 报告说明安全边界不仅是批准提示，还包括可写目录、网络策略、secret redaction 与 credential management。

**协议与扩展。** MCP 已成事实标准，也形成攻击面。Hou et al.（2025）统计 26 个目录中的数千个 MCP server，将威胁分为四类攻击者和十六种场景，包括工具投毒、rug pull 和跨 server shadowing。NSA 将 MCP 安全视作贯穿协议设计、运行调度、外部集成与长期监控的生命周期问题。Agent-first 工具设计还应提供 search、resolve、preview、execute、verify、recover，而不只是面向人的 CRUD。MCP、plugin、skill、SDK 与 agent-to-agent protocol 共同构成工具供应链，需要身份、allowlist、版本、审计日志与撤销。

**软件架构。** 分层架构、RBAC、浏览器沙箱和多智能体理论分别为五层拆分、权限模式、进程隔离和子智能体委派提供理论背景。

**本文定位。** 既有工作多研究 benchmark、框架和产品；本文贡献是对生产编程智能体进行有源码依据的设计空间分析，识别问题、映射替代方案，并与不同部署情境的 OpenClaw、Hermes 比较。

## 12 讨论

前文记录了 Claude Code 对循环、安全、扩展、上下文、委派和持久化问题的回答。每个回答都位于具有真实替代方案和可测权衡的设计空间。本节把这些答案合起来，讨论设计理念、价值张力、架构权衡、实证预测、限制、发展方向和跨子系统承诺。

### 12.1 设计理念

第 2 节的价值与原则预示系统会投资运行基础设施而非决策脚手架。实现也证实：权限门、工具路由、上下文管理和恢复逻辑等确定性基础设施占绝大多数，LLM 只是无状态 completion endpoint。估计 1.6% 为决策逻辑、98.4% 为运行 harness，并非偶然。Harness 创造让模型作出良好决定的条件，而不是限制其选择。

这与 LangGraph 的显式图节点、Devin 的多步规划器等主流模式相反。Claude Code 在丰富 harness 内给予模型最大决策自由；工程复杂性用于使决定成为可能，而非约束决定。这让 agentic coding tool 类似操作系统：循环像 kernel，其余部分像 OS。

当前沿模型在编程能力上趋近，外围 harness 质量可能成为主要差异。原生运行时 benchmark 固定模型、只换 harness，长时域任务得分可相差最多 18 分，测试对象包括 Claude Code 与 OpenClaw（Ding et al., 2026）。这支持把资源投入确定性上下文、安全与恢复，而不是继续加规划脚手架。

即使更强模型（文中以 Fable 5 为例）能自行读库修复，harness 仍服务五项价值。模型变强主要减少“能力放大”中的决策脚手架需求；可靠执行仍受有限窗口、恢复与非确定性实现影响；安全与能力无关，强模型甚至风险更高；人类决策权威关乎人的权利；情境适应仍需要 `CLAUDE.md`、skills 与 MCP；token 经济也不会消失。研究发现仅更换 harness，就能让最强模型的功能与安全通过率相差十个百分点以上（Compagna, 2026）。

总体而言，Claude Code 形成一个连贯设计点：在丰富运行 harness 内优先给予模型自主性。后文研究这一假设在哪里受到考验。

### 12.2 价值张力

五项价值彼此会产生结构性张力，并非设计失败。

### 表 6：价值之间的张力

| 价值对 | 张力 | 证据 |
|---|---|---|
| 权威 × 安全 | 审批疲劳 vs. 保护 | 93% 批准率削弱警觉；需由分类器与沙箱补偿 |
| 安全 × 能力 | 性能 vs. 防御深度 | 超过 50 个子命令时因解析成本跳过逐命令 deny |
| 适应性 × 安全 | 扩展能力 vs. 攻击面 | 多个 CVE 利用 hook/MCP 在信任建立前初始化 |
| 能力 × 适应性 | 主动性 vs. 干扰 | 多完成 12-18% 任务，但高频主动建议降低偏好 |
| 能力 × 可靠性 | 速度 vs. 一致性 | 有限上下文阻碍全库认知，子智能体隔离限制一致性，相邻工具观察到复杂度上升 |

长期能力是另一条问题线。16 名资深开发者完成 246 个任务的 RCT（Becker et al., 2025）发现，AI 使实际速度慢 19%，参与者却感觉快 20%。807 个仓库的 Cursor 因果分析发现复杂度增加 40.7%。54 人 EEG 研究发现 LLM 用户神经连接减弱，且移除 AI 后仍持续。2023-2024 年初级技术岗位招聘还下降 25%。这些研究不专门针对 Claude Code，却提示能力放大与长期可持续性的张力可能扩展到整个开发者培养管线。

### 12.3 架构权衡

**安全 vs. 自主。** 权限模式从 plan、default、acceptEdits、auto 到 bypassPermissions，自主性递增、安全提示递减；恢复时不还原权限体现向安全倾斜。用户实际并非总在理性选择模式，而会逐渐习惯：少于 50 个 session 时自动批准约 20%，到 750 个时超过 40%，session 也明显变长。沙箱估计减少 84% 权限提示，说明正确的人因应对是减少需要人决定的次数。

纵深防御假设各层独立，但 classifier 有 token 成本，Bash AST 棖查有解析延迟，deny 评估依赖命令结构；性能压力可能让多层同时退化。评估重点不应是“某层能否绕过”，而是需要多少独立层同时失败，以及它们是否共享故障模式。

**对抗条件下的权限模型。** 两个独立验证漏洞共享“信任建立前初始化”的根因：project hook、MCP 连接和 settings resolution 在交互信任对话框前运行。这个窗口位于 deny-first 流水线之外。图 4 展示空间上的检查顺序，却没有展示会话初始化的时间维度。扩展先加载、后显示 trust dialog、再全面执行权限，意味着可扩展性不仅因组合复杂度形成攻击面，也因初始化顺序形成攻击面。⁵

**上下文效率 vs. 透明度。** 五层压缩有效，但用户通常看不到丢失什么：超长工具输出被替换为引用、collapse 用摘要替代消息、snip 删除旧历史、microcompact 又受不可见 cache 决策影响。外部研究还指出摘要是阻塞推理停顿，并且不确定：相同输入不同运行保留内容会波动（Cim et al., 2026）。

**简单 vs. 扩展。** 四机制产生组合交互：插件 hook 改输入；classifier 读取缓存 `CLAUDE.md`；路径规则在读新目录时懒加载，可能中途改变 classifier；权限处理器四分支又在多个位置与 hook 交叉。由此产生难从单一配置预测的涌现行为。

⁵ 两个漏洞为 CVE-2025-59536（CVSS 8.7）和 CVE-2026-21852（CVSS 5.3）；其他位置还有 CVE-2025-54794、CVE-2025-54795。披露后数周内均修复。

### 12.4 实证预测与早期信号

有限窗口无法让 agent 同时感知全库；每层有损压缩都可能增加模式重复和违反惯例。子智能体在独立窗口、独立工具池工作，会进一步导致并行 agent 重复实现已有方案。局部好决定在缺乏全局上下文时可能产生糟糕整体结果。

相邻工具的研究与此一致。807 个仓库中，Cursor 初期速度提升到第三个月消失，复杂度显著增加，且复杂度上升与未来速度下降相关。对 6,275 个仓库中 304,000 个 AI commit 的审计发现可测技术债，约四分之一 AI 引入问题保留到最新版本，安全问题留存率更高。Claude Code 的 controlled minimal-pair study 则发现，代码整洁度不改变任务通过率，但干净输入减少 7-8% token 与 34% 文件重访。这说明 harness 上下文处理更明显影响成本与导航，而不一定影响原始成功率。

Claude Code 试图以渐进压缩、缓存感知、保留完整历史的读取时投影和子智能体摘要隔离缓解问题。是否足以克服有限上下文，是源码分析无法回答、但可直接测量的问题。

### 12.5 限制

`getSystemContext()`、`getUserContext()` 用 lodash memoize，因此 Git 状态和 `CLAUDE.md` 被缓存，不会每轮重算。对话中的动态变化可能无法立即反映；压缩清 cache 和路径规则懒加载提供部分补偿。

Feature flag 使构建不同。例如 `TRANSCRIPT_CLASSIFIER=false` 时整个 auto classifier 被裁掉；受 flag 控制的模块使用动态 `require()`，因为 Bun tree-shaking 约束下 `feature()` 只能出现在 if/ternary。不同构建目标可能得到功能不同的应用。

### 12.6 新兴方向

更长窗口可降低压缩压力；多模态工具会扩展动作表面也带来新上下文压力；对 deny 优先、沙箱不可逃逸、恢复不继承陈旧权限等性质做形式验证，可提供更强保证。

**架构解耦。** Managed Agents 将 session、harness、sandbox 虚拟化为可独立失败和替换的接口，类似 OS 把硬件虚拟成进程与文件。更强模型不是消灭 harness，而是移动有用组合的空间。云 agent 报告也把 agent loop、机器状态、对话状态、VM checkpoint、网络、secret 与 credential 视作产品组成。关键问题变成：哪一层拥有循环、状态、沙箱、策略和恢复路径？

**记忆成为一等子系统。** Agent memory 正从窗口管理副作用转变为独立认知基底，开放方向包括自动管理、RL 驱动和可信记忆。Claude Code 当前有事实层（`CLAUDE.md`、auto memory）和工作层（窗口）；自然下一步是经验层：跨会话自动积累并整理策略 playbook。Context Hub 把 `AGENTS.md`、skills、policies 与示例作为可版本、审查和部署的 artifact，指出上下文不仅需要 token 预算，还需要生命周期。

**可观测性与静默失败。** 行业报告估计 78% AI 失败不可见；1,340 人调查中，可观测性采用近 89%，离线评估只有 52.4%，质量而非成本是生产首要障碍。Claude Code 可查看工具调用、hook 和转录，但填平评估缺口可能需要 generator-evaluator 分离、sprint contract 和事后检查，而不只是更强模型。OpenAI 的改进循环把 trace/feedback 变成 eval，再形成 Codex harness 修改 handoff；telemetry 的价值在于转成可复用测试或具体变更请求。

**治理。** AI agent 自主行动使人更难在损害前介入，Agent Index 中仅 13.3% 系统发布专门 safety card。EU AI Act、版权讨论等可能对日志、透明、风险管理和监督施加外部约束。

**主动架构。** Feature-gated KAIROS 展示从反应式工具使用向持久后台 agent 演进：无用户消息时注入周期 `<tick>`，模型选择行动或睡眠。主动助手研究显示完成率提高 12-18%，但高频时用户偏好下降。KAIROS 结合终端焦点感知和 `SleepTool` 经济节流；每次唤醒都要 API 调用，闲置五分钟 prompt cache 过期。是否已在生产构建启用无法确认。

### 12.7 反复出现的设计选择

**以渐进分层取代单体机制。** 安全有七层、上下文有五层压缩加懒加载和摘要返回、扩展有四机制。它们以简单与易调试换纵深防御，并接受层间交互难预测。OpenClaw 与 Hermes 也出现渐进分层，说明它来自共同设计问题，而非 Claude Code 特例。

**Append-only 优先可审计性而非查询能力。** 转录是 JSONL，消息链读取时修补；权限不跨会话恢复；压缩对完整历史做投影而非破坏修改。它保留 resume、fork、audit 能力，代价是“跨会话查所有修改文件 X 的调用”需要事后重建。

**确定性 harness 内的模型判断。** Harness 建立工具路由、权限、上下文和恢复条件，模型自由决定调用什么、以何顺序调用。1.6% 决策逻辑比例对此作了量化。代价仍是有限上下文下，局部好决定可能形成整体坏结果。

## 13 未来方向

### 13.1 静默失败与可观测性-评估缺口

这一缺口可能来自缺少工具层、harness 内缺少评估接口，或模型能力上限，现有资料尚不能裁决。Cemri et al.（2025）整理系统设计、agent 间失准与任务验证等十四种失败；Pathak et al.（2025）构建专门检测轨迹异常的 benchmark；`pass^k` 衡量 k 次独立尝试全部成功的概率；Kapoor et al.（2024）指出 benchmark 缺 holdout 与成本控制。

开放问题有两个：generator-evaluator 分离、sprint contract、post-hoc check 等脚手架应进入 harness（例如新增 hook），还是作为外部评估层？现有 27 事件的 hook 流水线能否在当前上下文成本内承载它？这把工作定位在 harness，而不只是模型层。

### 13.2 持久化：记忆与长期同事关系

当前一端是静态 `CLAUDE.md`/auto memory，另一端是单会话 append-only 转录。中间缺少既非静态指令、也非单会话历史的持久状态。已有研究提出分页记忆式 LLM OS、可跨重启生产记忆、agentic memory、可复用过程轨迹和跨尝试自反思。MemGym 进一步评估工具对话、深度研究、编程与 computer use 中动态形成记忆，把问题从“笔记放哪”变成“记住什么才能持续正确工作”。

人机关系也会积累。P&G 776 名专业人员的实验、Copilot rollout 和 AI 团队纵向研究都观察到协作动态变化。开放问题是：同一基底能否同时承载个人指令层和组织共享上下文，又保持文件透明；会话权限又如何与其交互，不重新引入第 9 节拒绝的陈旧授权继承。OpenClaw 的 dreaming/daily notes/hybrid retrieval 与 Hermes 的 WAL SQLite/full-text search 提供两个参照点。

### 13.3 Harness 边界演进：在哪里、何时、对什么、与谁行动

- **在哪里（Where）：**Managed Agents 把 session、harness、sandbox 虚拟化为可替换接口；另有研究把 harness 当编译目标。
- **何时（When）：**主动性研究探索何时建议或行动，并量化完成率收益与高频打扰惩罚。
- **对什么（What）：**Vision-language-action 把 harness 从文本工具扩展到物理动作；此时可逆性加权风险面对比文本更大的成本不对称。
- **与谁（With whom）：**角色分化多智能体、multi-agent debate 和图结构工作流提供父/子模式之外的选择。

单一 harness 能否覆盖四轴，还是会分裂为专业栈，仍未知。跨轴组合也超出单子系统分析能力，并引出托管服务治理和物理动作可逆性问题。

### 13.4 时域扩展：从会话到科学计划

可靠执行既包括单轮正确，也包括长时域可靠性。现有基本单位是 turn、session、subagent；研究正在探索端到端自主科研、跨数日假设生成、算法发现以及 frontier agent 能以固定可靠率完成多长任务。Quantitative Goal Persistence 揭示更窄的失败：agent 可逐步做出合理调用，却在 verifier 确认足够有效工作单元前停止。长任务需要外部“完成”定义，而非流畅终答。

当多个 session 组合成长达数周的程序时，第 7 节上下文、第 8 节只返末条文本、第 9 节 append-only 是否仍足够？需要跨会话记忆，还是需要超越 session/subagent/memory 的协调原语？

本文分析快照后的 v2.1.154 引入 Dynamic Workflows：模型编写 JavaScript 编排脚本，后台运行时执行，最多扇出一千个 subagent；中间结果保存在模型上下文外的脚本变量（Anthropic, 2026i）。它把编排逻辑移出对话，正是新的长时域原语。Orchestration-as-code 是否成为主流，其 token 成本和减少的运行中人工监督如何与可靠性收益权衡，仍开放。

### 13.5 大规模治理与监督

新监管对 Anthropic-operator-user 权威层级施加外部约束。GPAI Code of Practice、实施指南、Agent Index 和国际 AI 安全报告推动更明确的文档、风险管理、透明与监督。训练数据来源判例和 AI 代码版权问题分别约束输入与输出；OECD 与早期合规研究勾勒监管接口但未规定细节。

监管也可能直接影响模型可用性，而不只是要求披露。文中举 2026 年 6 月美国出口管制导致 Fable 5、Mythos 5 先禁止外国人使用、随后 Anthropic 全球关闭的案例。Agentic benchmark 还把安全对象从文本转向环境状态，例如评估渐进攻击下多轮工作区编辑是否变得不安全；对编程 agent，风险对象可能是被修改的仓库，而非最终回答。

当前 deny-first 可经内部转录审计，却未必以监管框架要求的形式对外审计；“价值优先于规则”能否提供合规所需的明确规则表达，也是 harness 需要开放接口的问题。

### 13.6 开发者长期能力

第 2.4、12.2、12.4 节列举了感知与实际生产率差异、理解损失、复杂度累积、技术债留存、神经连接变化和初级招聘下降。Karpathy（2026）概括：“你可以外包思考，但不能外包理解。”未来系统能否把可持续性缺口作为一等设计问题，而非下游评估指标？

这也关系过程监督。人机协作规划研究认为用户需要过程级控制，而不只是结果审查；对 coding agent，对应问题是人在工作展开时能检查和修改什么。

需区分两个子问题。第一，现有长期效果能否在 session 粒度测量；当前 harness 没有理解度或惯例漂移信号，相关研究正提出交互、代码安全和认知卸载的 session 级测量。第二，得到测量后，架构如何回应：把 generator-evaluator 思路应用到人类循环、设计保护理解的表面，还是采用尚未命名机制？本文不选择机制，也不确定行动应位于 harness、IDE、组织还是人的发展循环。

## 14 结论

生产级编程智能体可以理解为对一组反复设计问题的回答：推理相对 harness 位于何处；执行、安全、扩展、上下文、委派与持久化如何组织；这些选择编码了哪些权衡。Claude Code 在空间中占据清晰位置：给予模型广泛局部自主性，同时用密集确定性 harness 包围它，负责权限、工具路由、上下文压缩、扩展和会话恢复。

从五项价值和十三项原则看，这些选择不是临时拼凑，而是始终优先考虑人类决策权威、安全、可靠执行、能力放大和情境适应性。

OpenClaw 与 Hermes 的比较说明，同样问题在不同系统反复出现，却得到不同答案。Claude Code 在 CLI harness 内投资逐操作分类与渐进压缩；OpenClaw 在多通道 gateway 内投资边界访问控制与结构化长期记忆；Hermes 用一个进程把逐操作审批呈现到多个表面，并提供可插拔记忆/模型后端。三者还能通过 ACP 多位置组合。

对 agent 构建者，最重要的开放问题不是如何增加自主性，而是如何长期保持人类能力。本文显示，当前架构很少有机制明确保护长期理解、代码库一致性和开发者培养管线。未来系统可以把这一可持续性缺口作为一等设计问题，而不是事后的评估指标。

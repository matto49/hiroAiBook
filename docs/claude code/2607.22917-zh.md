## 摘要

大语言模型（LLM）智能体显著改善了编码与编程工作流。Claude Code 尤其如此：它是能力最强的 LLM 编程智能体之一，可以执行复杂的编码任务。然而，若工作持续较长时间，几项缺陷会破坏智能体式工作流：

1. **Agent Team 无法恢复。** Agent Teams 功能很强，但每位 teammate 积累的工作状态会在进程停止后丢失，无法继续。例如，关闭终端就会导致这种情况。
2. **Compaction 会侵蚀工作细节。** Compaction 把对话压缩成摘要，因此智能体掌握的具体工作细节可能变得模糊。
3. **智能体式“技术债”。** 随着时间推移，用户的决定与智能体的操作会被困在已经压缩的旧对话中，项目越来越难维护和审查。
4. **提示词编写负担沉重。** 分配任务或交接工作时，用户必须反复重写很长的提示，才能获得期望的智能体表现。

我们提出 ATWZ（Agent Team Work Zone）：构建在 Claude Code 原生 Agent Teams 周围、以文件系统为基础的运维层，用来解决上述痛点。其核心设计思想是把每个 agent 和 teammate 都当作一名人类员工，并把他们的重要工作状态保存在一个称为“workstation（工作站）”的专用目录内，同时提供使用和维护这些文件的 skills、hooks 与 scripts。

有了 ATWZ，Agent Team 可以周期性地备份自身状态，使智能体在 compaction 之后恢复知识；进程结束后，可以用一条命令重建团队；这些机制也会显著缓解前述智能体式“技术债”。此外，在 ATWZ 内部，智能体“员工”可以互相发送文档，大幅减少编写提示词的工作量。

本文把 ATWZ 作为一份开发者导向的设计手册来介绍：说明设计及其理由，以场景和“用该层构建该层自身”的实践加以展示，并分析它的故障模式和局限。本文不报告基准测试或用户研究；实证评估留待未来工作。ATWZ 已开源：<https://github.com/SR-A-W/agent-team-work-zone>。

> **Dogfooding。** ATWZ 本身由运行在 ATWZ 上的 Claude Code Agent Teams 开发。换言之，这个层是在自身使用过程中迭代出来的。

## 1 引言

编程智能体已经强到可以不再一次只运行一个，而是作为团队运行：由一个协调者，也就是 team lead，拆解任务并把它们委派给专业成员；Claude Code 直接支持这种模式。可是，这样构建的团队会继承底层智能体的一项性质：它的状态存在聊天 session 里。每位 teammate 都是拥有独立上下文窗口的活动进程；一旦承载它的 session 停止——例如 SSH 断线、终端关闭或进程重启——teammate 也随之消失。

Lead 的 session 可以通过 `/resume` 恢复，但 Claude Code 文档明确指出，这不会恢复 session 内正在运行的 teammates；它们必须重新构建 [1]。Compaction——为了让长对话留在上下文窗口内而执行的摘要化——则会以更缓慢的方式侵蚀同一种状态。

**图 1：Agent Team Work Zone 总体架构。** ATWZ 是覆盖在 Claude Code 之上的文件式运维层。中间层的 agents 仍是临时进程；底层持久工作区使受到中断的团队能够被重新构建。

这一问题并非某个工具独有。OpenAI Codex 同样只提供为某项任务生成、完成后关闭的 subagents，没有能跨 session 持续存在的团队 [2]。对于短任务，这并无不妥；但当工作持续时间超过一次对话时，人类就会被迫成为团队的记忆与调度器，决定被埋入压缩过的聊天，谁做过什么也越来越不清楚。这形成一种智能体式技术债，使项目更难恢复、更难审查。

本文介绍 Agent Team Work Zone：一个围绕 Claude Code Agent Teams 构建的持久化与管理层。它唯一的根本设计选择，是把重要状态放到 session 上下文记忆之外的文件中。角色、工作上下文、决定、消息、任务文件和团队名册，都成为落盘的、按 agent 隔离的持久产物，再由一层很薄的 hooks、scripts 和 skills 与运行中的 Claude Code 连接起来。

Agents 仍然是临时的——ATWZ 不改变 Claude Code 运行它们的方式——但重建它们所需的信息会被写下来。在这一基础之上，ATWZ 增加了自动检查点、从检查点一键重建团队的重新激活流程、用于跨 session 通信和审计的文件式 inbox，以及关于角色、版本和发布的约定；整个过程始终有人类参与。图 1 展示了整体架构。

Claude Code 的 Agent Teams API 在 2.1.178 版发生变化，简化了团队注册层。本文覆盖两个版本，并以新 API 为主要讨论对象。在两种版本中，以文件取代上下文、设置检查点和一键重新激活的核心主张都成立。

本文是开发者导向的设计手册，而非实证研究。我们说明设计和理由，通过场景举例，并报告使用 ATWZ 构建自身时得到的经验；不提出基准测试或用户研究方面的结论。第 2–3 节说明背景和目标缺口；第 4–9 节展开设计，并在必要处标注版本差异；第 10 节整理故障模式和缓解措施；第 11 节讨论相关研究；第 12 节说明局限。

> **注 1：** 本文的“in-context memory”指 session 的上下文窗口。读写它很快，但 session 结束或发生 compaction 时便会丢失；任何未写入磁盘的信息都会随之消失。

## 2 背景：Claude Code、Subagents 与 Agent Teams

本手册直接建立在 Claude Code 的多智能体功能上，因此首先说明这些功能怎样工作，更重要的是，它们产生的状态会在哪里丢失。随后我们指出，同样的局限也存在于另一种广泛使用的编程智能体 OpenAI Codex 中；这意味着本文要填补的缺口，并不是某个工具的偶发现象。

### 2.1 Claude Code、subagents 与 Agent Teams

Claude Code 是命令行编程智能体：用户与一个能读取和编辑文件、运行命令并朝目标反复迭代的模型对话，所有操作都发生在一个 session 内。两项功能使一个 session 能够调动多个 agents。

**Subagents 是轻量级的委派对象。** 主 agent 可以生成一个拥有独立上下文窗口、工具权限和系统提示的 subagent，让它处理边界明确的一块工作，并接收其返回结果；多个 subagents 可以并行运行。它们的作用域是单个 session：文档写明“subagents 在单个 session 内工作”，每个 subagent 在自己的上下文窗口中运行，然后把结果返回调用者 [3]。

**Agent Teams 是一项由环境变量启用的实验功能。** 它走得更远：一个 team lead 协调多个相互独立的 Claude Code 实例。Teammates“独立工作，各自拥有上下文窗口，并能直接彼此通信”；lead 从共享任务列表分配任务并综合结果 [1]。Claude Code 还有其他同时运行多个 session 的方法，例如 agent view 可以派发独立的后台 session，但这些 workers“只向你汇报”。只有 Agent Teams 的 workers 由 lead 协调、共享 session 任务列表并彼此发消息 [4]，因此本文建立在 Agent Teams 之上。

> **注 2：** “只存在于 session”并不等于完全没有持久化。文档记录了两种需主动启用的 subagent 持久化形式：在仍然活跃的 session 内，可以通过发消息来恢复带完整对话历史的 subagent；进程重启后，则只能通过恢复同一个父 session 来恢复它。另一个可选 memory 目录会给 subagent 一个“跨对话保留”的文件夹。但这两者都不会在 session 消失后继续保留一个活动参与者。事实上，memory 目录采用的正是本文推广的办法：把需要持久存在的部分放进文件。此处依据 2026 年 7 月文档。

### 2.2 状态去了哪里

两种机制都把 session 设为 agent 自身的持久边界：subagents 默认如此（另有上述可选出口），Agent Teams 则被文档明确列为限制：`/resume` 与 `/rewind` 不会恢复进程中的 teammates。恢复 session 后，lead 可能尝试向已经不存在的 teammates 发消息；遇到这种情况，需要让 lead 生成新的 teammates [1]。

关键就在这种不对称：`/resume` 能恢复 lead 的 session，却不能恢复 teammates，它们必须重建。Teammate 的丢失与版本无关，因为它们都是活动进程；无论版本怎样，session 重启都会终止它们。

团队落盘的脚手架——config 与 task list——在不同版本中的行为不同：

- **2.1.178 之前。** 即使运行时注册已经消失，落盘状态仍会保留。死亡 teammate 的条目作为过期“幽灵”残留在团队目录中，后续运行必须处理它。
- **CC ≥ 2.1.178。** 系统改为自动创建、仅限 session 的 `session-<id>` 团队，并在退出时清理：“session 结束时会移除 team config 目录”，而“task list 目录在本地持续存在且从不上传，因此恢复的 session 会保留任务”[1]。新版本还会自动清理由团队退出的 teammates，从而消除旧 API 的幽灵条目和 `Name-2` 名称漂移问题。

**图 2：session 结束时会摧毁什么。** 此图以 2.1.178 之前的版本绘制。被摧毁的包括 teammate 进程、团队的内存协调状态，以及只保存在上下文窗口中的工作信息。Lead session 可以 `/resume`。旧版本会在磁盘留下过期的团队目录；CC ≥ 2.1.178 则会在退出时清理 session 范围的 team config。无论哪种版本，活动团队都不会自行回来。

因此，一个 session 停止时，三项内容会一起消失：teammate 进程、团队在内存中的协调状态，以及只在 teammate 上下文窗口中保存的工作信息。曾有人请求让 subagent session 可恢复，但该请求在 2026 年 1 月被 inactivity bot 关闭，而不是被维护者否决；之后 Claude Code 加入了 session 范围的恢复，但并没有提供该请求所要求的跨 session 接口 [5]。

Compaction 是同类损失的温和版本。它把对话压缩为摘要，以适应上下文窗口，可能使 agent 对自身角色、当前任务和未完成承诺的认识变得模糊。

> **注 3：** CC ≥ 2.1.178 的 session 团队会自动清理已经退出的 teammates，因此不再存在幽灵条目和 `Name-2` 漂移。但 teammate 进程在新旧版本中都仍是临时的；重启 session 仍会终止全部 teammates。

> **注 4：** Compaction（`/compact`）把活动上下文窗口重写成浓缩摘要，速度快但有损。最常见的牺牲品是角色定义、细致决定和尚未履行的承诺。

### 2.3 Codex 中也有同样的形态

这不是 Claude Code 独有的问题。OpenAI Codex 提供 subagent 工作流：主 agent 并行生成专业 agents，在一个响应中收集结果，并在任务完成后关闭 agent threads [2]。其 cloud 模式运行委派任务，每个任务拥有独立环境，并返回 diff 或 pull request [6]。两种模式都没有跨 session 保持的、具名的常驻团队；唯一持久的是以磁盘配置保存、可重复使用的 agent 定义，而非活动 agent 实例。

因此，在两种工具里，多智能体 primitive 都是临时的：它很适合并行处理边界明确的任务，却不能维持一个跨越多个 session 的团队。

> **注 5：** 截至 2026 年中，文档曾写明“只有明确要求时，Codex 才会生成 subagents”。后来该文档移至 ChatGPT 网站，并同时说明 ChatGPT 与 Codex；截至 2026 年 7 月，更高等级允许主动委派，使 ChatGPT 无需额外请求便可委派合适的独立工作。改变的是由谁发起 subagent，而不是其生命周期：threads 仍会在完成后关闭，也没有引入常驻团队。

### 2.4 由此产生的缺口

这些工具已经具备非平凡项目真正需要的能力：几个专业 agents 在协调者之下共同工作。但它们缺少连续性——没有办法把团队及其积累的理解带过 session 结束这一边界。

本文余下部分的起点，就是在不改变 agents 自身运行方式的前提下填补这一缺口。

## 3 缺口与问题陈述

第 2 节留下了一个明确问题：Claude Code 允许团队工作，却不能让团队持续存在。ATWZ 针对以下缺口；每一项都是未经辅助的 Claude Code 会失去长期项目连续性的地方。

- **Teammates 无法跨重启生存。** Lead session 结束后，teammates 及其工作状态消失，没有原生方法让它们回来；用户只能重建团队并重新解释上下文。
- **Compaction 丢失细节。** 摘要化对话会模糊 agent 的角色、当前任务与未完成承诺。
- **不同 session 的 agents 无法交谈。** 独立对话之间没有通信渠道；团队内部消息也不会在 session 结束后保留。
- **任务和决定状态没有与项目共存。** 平台 task list 在 session 结束时虽不会立即删除，却位于项目目录之外，而且只记录任务项。做了什么决定、为什么这样决定、完成了什么，并不会在工作旁边留下持久、可检查的轨迹，导致推理被重复或遗漏，变更也难以归因。甚至 task list 也会被保留期定时器清理；与清除 session transcript 的计时器相同，`cleanupPeriodDays` 默认是 30 天 [7]。
- **交接依赖重新输入。** 把任务移交到另一个 conversation，意味着手工重写背景、目标和约束。

CC ≥ 2.1.178 的平台持久化把这个缺口表现得非常清楚：恢复的 session 能找回 session task list，工作项还在；但进程中的 teammates 已不复存在。回来的是“这一轮运行”——一份待办事项清单——却没有任何人来执行。没有回来的是团队：它的角色、积累的理解和未完成承诺。本文余下部分要做的，就是让这些内容持久化。

我们在 workspace 层而不是 model 层处理这些问题。ATWZ 不修改 Claude Code agents，也不提出新的 agent 算法；其贡献是一组基于文件的约定，以及配套 hooks、scripts 和 skills，为 Claude Code Agent Team 提供连续性、可恢复性和审计轨迹。

有一条边界必须直说：ATWZ 不会让 teammate 进程跨 session 存活，也不声称拥有平台本身未提供的持久化。这里的恢复是依据持久文件进行**重建**：新的 teammate 重新阅读前任留下的内容并从该状态继续，而不是保存一个活动进程。

一个合理质疑是：如果 lead 恢复自己的 session，然后重建 teammates，这和在父 session 内恢复 subagent 有何区别？流程仪式确实相似，但有三处不同：

1. 单位是团队而不是单个 agent：这是一份包含角色、工作范围和未完成承诺的名册，平台没有等价物。
2. Artifact 是“创作出来的”而非“直接捕获的”：checkpoint 是作者专门为继任者写的摘要，有意舍弃部分信息，而且人类可读；它不是原始 transcript。
3. Artifact 位于项目内，因此可纳入版本控制、可审查，而且不受平台保留期限约束。恢复原 session 只是给 lead 的便利条件，不是前提；一个位于同一项目中的全新 session 也可以读取 registry 与 workstations，重建团队。

> **注 6：** 这是 reconstruction，而不是 preservation。新的 teammate 重新阅读前任写下的状态并从那里继续，没有任何活动进程被带过边界。

## 4 设计哲学

### 4.1 运维层，而不是替代品

Agent Team Work Zone 不改变 Claude Code agents 的运行方式，而是用文件式运维层包裹它们。它把平台已有的长处——文件 I/O、项目本地 skills、自定义 agents、hooks 和 Agent Teams——作为前提，再补充长期项目所需的外围能力。

说得直接一些：Claude Code 让你生成 agents；ATWZ 帮你在对话结束后继续管理它们。所有设计都来自一条规则：未来 agent 会需要的任何内容，都必须写入 session 上下文记忆之外的文件。

### 4.2 状态放在文件中，而不是上下文记忆中

本文所谓 in-context memory，是模型当前在对话中持有的活动上下文窗口。它快速、方便，但会随 session 结束而消失，并被 compaction 稀释，也无法从外部检查。对 teammates 而言这种丢失是永久的，因为它们不能恢复；lead 则可以用 `/resume` 找回自身上下文。

ATWZ 把上下文视为工作区，而非存储区。任何需要比 teammate 活得更久的信息——角色、正在做什么、做过什么决定、还欠什么——都写入磁盘。

这不同于 Claude Code 始终加载的 `CLAUDE.md` 指令。后者最多存在于 managed、user、project 和 local 四种 scope 中，并且是“拼接进上下文，而非相互覆盖”；还可通过 `.claude/rules/` 下按路径生效的规则扩展 [8]。它很适合稳定的全局指令，但也是所有 session 自动消费的共享表面。

它也不同于 Claude Code 的 recall-based memory：后者通过 `MEMORY.md` 索引和“一主题一文件”的 notes，按相关性呈现事实，而非预先全部加载 [8]。Workstation note 与二者都不同：它只属于一个 agent，详细记录当前任务，按需读取而不是强塞进所有上下文窗口，并通过隔离防止一个 agent 的 notes 覆盖或污染另一个 agent。

三者可以互补：`CLAUDE.md` 保存始终加载的指令，Claude Code `memory/` 保存按相关性召回的事实，workstations 保存每位 agent 的操作状态。

**图 3：把状态保存在文件里，而不是易失的上下文记忆里。** 图中同时区分了每个 agent 的 workstation note 与 Claude Code 通过相关性召回的 `memory/`。

### 4.3 原则

文件优先规则导出六项贯穿设计的原则：

- **文件优于上下文记忆。** 如果未来 agent 会需要，就写下来。这是根规则，其他 primitive 都是它的结果。
- **Workstations 是工作笔记。** 每位 agent 都有外部 notebook，记录当前理解、失败路径、未完成承诺和恢复位置；它真正的用途是在 compaction 或重启后重建 agent。
- **低耦合。** 每位 agent 拥有自己的 workstation；其他 agents 只能通过 reports 与它交互，绝不编辑它的文件。
- **Reports 就是 prompts。** 优秀的 agent-to-agent report 是一份 prompt packet：发生了什么、尝试过什么、改动了什么、接下来需要什么、文件在哪里。
- **Lead 负责协调。** Team lead 把上下文用于拆解、路由、审查和综合；具体实现交给 teammates。
- **可审计性。** 完成的工作及其理由留在磁盘，不会随产生它们的对话关闭而消失。

### 4.4 两种形态，而不是强行一种

不是每个 agent 都应该变成团队。每个 teammate 在独立 session 中运行，所以 token 成本会随团队规模增长。简单工作或纯协调工作保持扁平结构——一个 agent、一个 workstation；只有确实复杂、需要多种专业能力或并行工作流的任务才组成团队。

目录结构也体现这种克制。Flat workstations 与 team workstations 并排存在；team workstation 的目录名以 `_team` 结尾，并包含 `roundtable/`、`teammates/` 和 registry 等团队内部子树，因此整个 roster 一眼可见。把 flat agent 晋升为团队，只需重命名并创建这棵子树；`/promote-to-team` 可以一步完成。

### 4.5 通过实际使用加固

这是方法而非机制方面的一点说明。ATWZ 的很多设计不是预先规划出来的，而是在实际工作中运行该层——包括用它构建自身——再把暴露出的失败固化成规则和机制。许多最尖锐的问题只在持续使用下才会出现，因此“用它管理自己，然后修复坏掉的地方”本身就是方法的一部分。第 10 节整理了由此得到的结果。

## 5 Workspace 与核心 Primitives

本节说明 ATWZ 安装的 workspace，以及其他设计赖以成立的少量 primitives。

### 5.1 Workstations

基本单位是 workstation：一个只归属于某位 agent 的持久目录，以文件而不是聊天记忆保存该 agent 知道、承诺或追踪的一切。

Workstation 有两种，由名称和结构共同区分。Flat workstation 是普通目录；team workstation 以 `_team` 结尾，并带有团队内部子树。晋升操作会同时建立这两项。Skills 在运行时只依据结构判断：目录名以 `_team` 结尾且包含 `roundtable/`，不需要配置文件或 flag；布局本身就是信号。

### 5.2 目录树

所有内容都安装在项目根目录的 `_agent_team_work_zone/` 下，使框架拥有的文件与用户拥有的文件分离：

```text
_agent_team_work_zone/
|-- README.md                  框架文档 + 标记块内的工作规则
|-- meeting_room/             顶层异步通信（所有 flat agents + leads）
|-- archive/                  已解决的 meeting-room 消息
|-- <agent>/                  FLAT workstation
|   \-- README.md notes.md TODO.md ACTIVE_JOBS.md COMPLETED_JOBS.md
|       （README.md：角色 + 完整工作规则）
|-- <agent>_team/             TEAM workstation
|   |-- README.md ... TEAMMATE_INFO.json
|   |   （registry：角色 + 完整规则）
|   |-- roundtable/           团队内部通信（lead <-> teammates）
|   |-- archive/ team_recipes/
|   \-- teammates/<name>/
|       \-- README.md working-context.md completed.md
|           TODO.md commitments.md
|           （README.md：角色 + 精简规则子集）
|-- resources/               框架拥有：skills、agents、
|                            role archetypes、scripts、hooks
\-- docs/                    框架拥有：manuals
```

这项拆分是升级能够安全工作的关键。截至 v0.3.2，升级会替换框架拥有的路径——`resources/`、`docs/`，以及 `README.md` 中带注释标记的 blocks（framework section、work rules 和 reference material，包括预装 skill、subagent 与 troubleshooting 清单）——但绝不碰用户拥有的路径，如所有 workstations、meeting room 和 archive。

`README.md` 内部的边界通过 comment markers 机械执行，因此升级只重写这些 blocks，项目特有内容会原样保留。

### 5.3 角色、Registry 与通信

后文会反复使用三种 primitive：

- **Role。** 简短定义 agent 的用途。它被存为文件，因此未来再次生成同一 agent 时可以继承角色，而不需要重新解释。
- **Team registry。** `TEAMMATE_INFO.json` 是 lead 拥有的 roster；lead 增删条目，每个 teammate 则在自己的 row 写入 checkpoint 时间。它列出团队成员及驱动恢复的 metadata，是 reactivation 的输入。
- **文件式异步通信。** Agents 通过两级空间协调：所有 flat agents 与 leads 共享顶层 meeting room；每个团队另有 lead 与 teammates 使用的 roundtable。二者都只是上述目录树中的文件，而这正是设计目的。

## 6 持久化与恢复

让 Claude Code Agent Team 穿过创建它的 session，是 ATWZ 的标志性问题。难点来自两项事实：Claude Code 不会持久化 teammate sessions，而且判断 teammate 是否仍然存活很容易出错。ATWZ 用基于持久 registry 与 checkpoints 的重新激活流程解决前者，用明确的 liveness rule 解决后者。Claude Code 2.1.178 改变了 session state 的管理机制，因此本节同时覆盖两个版本，并先介绍新 API。

### 6.1 跨 session 边界的团队状态

**新版本（CC ≥ 2.1.178）。** Claude Code 为每个 lead session 自动创建一个 session 范围的 `session-<id>` team。当 teammate 离开时，runtime 同步更新注册，不会积累 ghost entry，团队 membership record 始终保持最新。跨过 session 边界后，注册会在下一个 lead session 自动重建，因此操作者只需重建 teammates 本身。

平台 task list 不受该边界影响：它以 session 派生的名称存放，session 结束时不会删除其目录，因此恢复 session 会找回 tasks。

**旧版本（2.1.178 之前）。** 早期版本把 team state 保存在两个跨 session 行为相反的位置。Runtime registration 位于进程内存，session 结束时被摧毁；之后尝试把 agent spawn 进该团队会得到“Team does not exist”。落盘 team config 却会持续并不断积累：死亡 teammate 留下永不清理的 ghost entry，再次使用同名 spawn 会得到漂移后的 `Name-2`。

两者朝相反方向失败——一个消失了，必须重建；另一个残留了，必须清理——所以恢复流程会同时清理并重建二者。

### 6.2 Reactivation

**新版本（CC ≥ 2.1.178）。** 新 API 上的 `/reactivate-team` 没有 clearing step。Session team 已是干净状态，因此恢复会直接读取 lead 拥有的名册 `TEAMMATE_INFO.json`；然后为每个 teammate 生成一个新的 session，其首条指令是读取自己的 workstation：role file、checkpoint 和 commitments。

ATWZ skills 使用 `<slug>-<role>` 约定命名每个 teammate。Idle hook 从 slug 前缀推导 workstation path，这使解析没有歧义；名字不只是身份，也携带结构。

成功只能以一种方式判断：复活的 teammate 在当前 session 中发回一条消息。磁盘文件无法证明某次 reactivation 成功，因为一个 spawn 若在发消息之前死亡，所有文件仍会保持不变。证据是 receipt，而不是 artifact。

**图 4：CC ≥ 2.1.178 上的团队重新激活。** 读取 team registry，以 `<slug>-<role>` 名称将各 teammate spawn 进自动 session team，再让每位 teammate 从自己的 checkpoint 恢复；无需清理 registration。

**旧版本（2.1.178 之前）。** 旧版本上的 `/reactivate-team` 必须先在一个步骤内清除过期 config 并重新创建 registration，使 respawn 能重新取得原名而不是漂移成 `Name-2`；随后读取 registry，以相同的“读取自己的 notes”指令生成 teammates。余下流程相同：每位 teammate 读取自己的 workstation，并向 lead 发消息确认存活。

**图 5：旧版本上的团队重新激活。** 清除过期 registration，读取 registry，再次生成各 teammate，使其从自身 checkpoint 恢复。

### 6.3 如何知道 teammate 是否还活着

恢复最常见的错误，是在 teammate 实际已经死亡时假设它还活着。ATWZ 固定了一条规则：**只有由当前、从未中断的 lead session 生成的 teammate 才算活着。** 任何重启都会终止团队中的全部 teammates；resume 只能恢复 lead，不能恢复 teammates。

静态信号明确不构成证据：config entry 不算、inbox 中的一条 message 不算、人类写下的 `status: active` 不算，普通 reply 也不算，因为它不会跨过 agent boundary。唯一的正面信号，是本 session 向 teammate 发出新 ping 后，收到它通过 teammate channel 返回的消息。没有收到，只能判断为“unknown”；ATWZ 把 unknown 当作 dead。

由实践得出两项推论。第一，context compaction 发生在同一进程内，不会杀死 teammates，所以不应触发盲目重建。第二，receipt 会过期：几轮之前作过响应的 teammate 现在可能已经死亡，因此每次判断都需要新检查。另有较轻的第三种状态 `benched`：可以把 teammate 暂时下线以释放 slot，同时保留 workstation，之后再按名字唤醒。

> **注 7：** 在 CC ≥ 2.1.178 中，teammate 消息会带自动 session team 名称（`@session-<id>`）。这是正常路由信息，不代表 teammate 死亡，也不意味着它加入了另一支团队。

### 6.4 自动且非破坏性的 Checkpoints

Reactivation 的质量取决于 teammate 留下的状态，而保存状态不应依赖任何人记得手动执行。每位 teammate 维护一个 checkpoint file，其中包括：

- 当前状态快照：目标、活动任务、决定、开放问题、承诺和关键文件引用；
- 简短的追加式近期工作 journal：最新条目逐字保留最近几轮，旧条目则压缩为摘要，在控制日志体积的同时保留近期精度。

Reactivation 会读回该文件以重建 teammate。写 checkpoint 是非破坏性的：compaction 会重写活动上下文，而 checkpoint 只是读取上下文并写入文件，因此 teammate 可以在任务中途保存检查点，然后继续工作。

保存通过一个单向 hook 自动完成。Teammate 即将 idle 时，lead session 内的 `TeammateIdle` hook 会比较 Unix epoch 整数时间戳，检查该 teammate 上次 checkpoint 距今多久；采用整数时间能避开一类时区错误。

- 未达到阈值（15 分钟）时，允许进入 idle。
- 达到或超过阈值时，hook 返回非零状态，阻止 idle，并向 teammate 注入“立即 checkpoint”的提醒。
- 写入 checkpoint 会刷新文件时间戳，所以下一次 idle 能通过，循环自行制动。

系统还有 guard：连续提醒数次后会释放 teammate，避免把它永久卡住；遇到不确定性——缺少文件或工具能力不足——则 fail open，不会仅因怀疑就阻止 teammate。

**图 6：`TeammateIdle` checkpoint gate。** 基于文件年龄的 hook 阻止 teammate idle 并强制保存 checkpoint；时间戳刷新后，门控自行解除。

Release gate（第 9 节）故意采用相反的默认方向，因为同一原则“朝可恢复结果失败”在代价相反时会得出不同结论。漏掉一次 checkpoint，最多损失几分钟未落盘的上下文，下一次 idle 还会提醒；错误阻塞 teammate 则会停止工作。延迟 tag 的代价只是重跑，而错误 release 一旦发出就无法收回。

## 7 通信与审计

不同 session 内的 agents 无法直接对话，因此 ATWZ 为它们提供异步的文件式 channel，并规定一套使用纪律；这套纪律同时会留下审计轨迹。

### 7.1 两个 Channels，一套 Protocol

通信使用第 5 节介绍的两个文件空间：

- 顶层 meeting room：任何 flat agent 或 team lead 都可以使用；
- 每个团队的 roundtable：由该团队的 lead 与 teammates 使用。

二者采用相同 protocol，差别只在 agent 的寻址方式。每条 message 都是 Markdown 文件，frontmatter 保存其生命周期：status 按 `OPEN -> IN_PROGRESS -> RESOLVED` 变化，并包含 issuer 的 `from`、一个或多个接收者或全体成员的 `to`，以及可选、只读的 `cc`。

在 meeting room 中，agents 直接按名称寻址；团队内部则使用 `<team>/<role>`，另有 `kind` 字段记录 report 类型。文件名编码 author、type 与精确到分钟的 timestamp，因此消息可以按时间排序，不打开文件也能看出作者。

### 7.2 处理 Inbox

由于 channel 不会主动 push，agent 通过 `/check-inbox` 按需读取。该 skill 判断当前 agent 身份，扫描此身份有权读取的空间，把可操作消息按从旧到新排序——较晚任务可能依赖较早任务——并在执行前展示给用户确认。

之后，skill 逐项处理：标记为 in progress、执行任务、记录结果、标记 resolved；最后归档该 agent 自己发出且已完成的消息。

**图 7：文件式消息。** Agent 写一条发给另一 agent 的 message；接收者使用 `/check-inbox` 读取，完成任务并标记 resolved；之后由 issuer 归档。

### 7.3 为什么由 Issuer 归档

一条小规则避免了常见故障：只有 message 的 issuer 可以归档它。早期设计允许 recipient 归档，引发两个问题：

1. 有多个 recipients 时，每个人都以为别人会归档，resolved messages 因而不断堆积。
2. Recipient 可能在 issuer 看见完成结果之前就归档，使完成信号丢失。

把归档设为 issuer 的专属职责，就只留下一个明确负责方，而这个人必然先看见结果；多 recipient 消息由 issuer 维护 checklist 协调。Archive 永不清理，因为它是已经决定和完成事项的持久记录；正是这个记录，使产生工作的 conversations 关闭后，项目仍然可审计。

### 7.4 跨边界交接工作

当任务必须从一个 agent 移到另一个 agent 时，`/handoff` 会把它打包：进度、触及的文件、决定、开放问题，以及最容易在交接中丢失的内容——任务为什么存在。

包中建议的 next steps 明确没有约束力，receiver 可以自行选择方法。Originator 的 task file 会把该项标记为 handed off，而不是删除，因此轨迹仍然存在。

## 8 角色、生命周期与工作规则

团队由一位 lead 和少数 specialists 组成，通过一小组 skills 形成和维护，角色来自一个 role library，并遵守简短的 work rules。本节说明这套管理机制及其背后的工作纪律。

### 8.1 小型 Role Library

角色分为两层。ATWZ 自带五种通用 subagents，可直接复用：

- **tracker：** 用低成本模型周期性轮询状态；
- **reviewer：** 进行只读、分级的代码审查；
- **investigator：** 对“运行正常但结果错误”的情况进行假设驱动调试；
- **devil's advocate：** 在计划执行前进行对抗性审查；
- **git manager：** 带安全检查地执行版本控制操作。

每个角色使用的模型与其工作相匹配：机械式 polling 交给能够胜任的最低成本模型；结构化 review 使用更高一级模型；对抗性或生成假设的工作使用最强模型，因为“廉价但自信地犯错”比诚实的不确定性更危险。

除此之外，系统还提供九种 archetypes。它们是模板而不是开箱即用的 agents：例如，“coder”过于模糊，无法全局定义；archetype 只捕捉稳定类别和一份起始 prompt，其中明确写出“你不做什么”，防止并行 teammates 工作重叠。Lead 再根据具体任务填充细节。

### 8.2 生命周期

Workstation 从 `/onboard` 开始。该命令不会猜测，而是询问 agent 是 flat agent 还是 team lead。Flat workstation 的任务若变得过大，之后可原地晋升。

团队通过 `/spawn-team` 组成。这是一段简短流程：收集任务、拆解任务、提出人员配置，让用户确认，然后生成 teammates，并记录本次操作的 recipe。

团队运行后，lead 通过少量管理 skills 增员、审查、退休或临时 bench teammates。团队保持在三到五人，因为协调成本增长快于线性。Offboarding 是中性、正常的步骤；退休 teammate 的 workstation 会作为记录保留。Session 结束后，teammates 通过 `/reactivate-team` 返回 active 状态。

有两种反复使用的实践值得单独指出：

1. Teammate 进行较大变更前，先提交一份快速、只读的 plan，由 lead 审批；这样能把代价高昂的错误修改变成成本很低的审查。
2. 组建团队时可选用 adversarial reviewer，负责发现 failure modes，但没有 veto 权；最终决定仍由 lead 做出。

**图 8：团队生命周期的跨版本基线。** Spawn 后进入由工作与自动 checkpoints 构成的 active loop；成员可以被 bench 或 offboard；session 结束后可重新激活。图中还展示 lead 与 specialists 的 role roster，角色名仅为示例。CC ≥ 2.1.178 特有变化见图 9。

从用户角度看，大部分机制不可见。Management skills 可由 agent 自行调用，因此用户只需用自然语言给出任务，lead 决定是否组队、添加谁和 bench 谁。

**命名与权限（版本说明）。** 在 CC ≥ 2.1.178 中，ATWZ skills 按 `<slug>-<role>` 约定命名每位 teammate，例如 `architect-typesetter`。这不是装饰：idle hook 可以从 slug prefix 确定地推导 teammate 的 workstation path，在运行时使用 `${name%%-*}_team` 解析。

Legacy name 仍可通过对 workstation tree 执行 guarded glob 来解析；但如果该名字在多个团队中不唯一，fallback 会放弃解析，静默丢弃两个团队的 nudge。旧版本的 hook 直接从 idle event 的 team name 解析 workstation，因此任何 teammate 名称都可使用。

**图 9：CC ≥ 2.1.178 上的生命周期补充。** `<slug>-<role>` 是 skills 强制采用的命名约定，使 idle hook 能无歧义地从 slug prefix 推导 workstation path。旧版本则从 idle event 的 team name 读取该路径。

两种版本都会从 lead session 继承 permission mode，而不是在 spawn 时为每位 teammate 单独设置。若要让 teammates 以 `auto` mode 运行，必须在 spawn 之前把以下配置写进全局 `~/.claude/settings.json`：

```json
{
  "permissions": {
    "defaultMode": "auto"
  }
}
```

Claude Code 会忽略 project 和 local 层级中的这个 key。

### 8.3 工作规则

Skills 之下是一组简短的行为规则。ATWZ 把“怎样把规则送到 agent”视为机制问题，而不是口头劝告。

Flat workstation 或 lead 的 role file 会逐字携带完整规则集；升级会原地刷新这些规则，所以 compaction 后重读该文件，可以按最新版本重新加载规则。Teammate role file 携带精简子集，只包含约束其自身行为的规则。`/spawn-team` 创建 workstation 时会写入这些规则；spawn 与 reactivation prompts 还包含 self-heal step，用于修复旧版本创建的 workstations。

这些规则把前文哲学落实到日常行为：

- 每位 agent 只拥有并维护自己的文件，不编辑他人的文件，只通过 messages 行动；
- Reports 必须能够独立理解；
- 只有 issuer 可以归档；
- Task state 和 working notes 与项目一起存在文件里，而不是只存在于 session task list；
- Lead 把上下文用于协调，而不是实现；
- Teammate 始终保持 checkpoint 最新。

与其说这是一部规则书，不如说它是“文件优先”哲学在日常行为中的书面形式。

## 9 版本与发布

ATWZ 是一种 template，下游项目会安装它并在以后升级，所以部署有一项硬要求：升级必须更新框架，但绝不能触碰用户自己的工作。

第 6 和第 8 节的版本差异映射到一条线性 release line，以 Claude Code 2.1.178 API 变化为分界：

- `v0.1.0` 是旧 API（CC ≤ 2.1.177）唯一且最后的 release；该版本冻结，不再接受变更。
- `v0.2.0` 及之后面向新 API（CC ≥ 2.1.178），后续开发在此线上继续。
- 截至 2026 年 7 月，当前版本为 `v0.3.2`。

使用旧 runtime 的项目安装冻结 release 并停留在那里；新 runtime 项目沿持续开发线升级。这样，项目拿到的 team state、命名和 reactivation 机制与其 runtime 一致，不会混合新旧 API。

### 9.1 安装与升级

部署依赖少量 scripts。Bootstrap 先检查环境版本，再把框架 skills 与 agent definitions 同步进项目 `.claude/`；它会创建或合并 settings，而不是覆盖。一个 thin installer 封装首次安装；one-button upgrade 拉取最新版本，然后交给 migration step。

Migration logic 从刚下载的新版本运行，因此执行升级的代码总是最新代码。

第 5 节的 ownership boundary 是安全基础。升级时替换 framework-owned paths；user-owned paths——每个 workstation、meeting room 和 archive——永不触碰。在唯一混合两种所有权的文件 framework README 中，comment markers 划定 framework blocks：framework section、work rules 和 reference material。升级只重写这些 blocks，逐字保留 project-specific content。

Pre-flight check 会在删除任何 target 前，确认每个 replacement source 都存在，因此升级不会让项目陷入“旧框架已删、新框架却不存在”的状态。

### 9.2 Migrations 与 Release Gates

跨越多个版本的升级，会执行一串 version-to-version steps。每一步结束时写入新版本号，因此升级失败后可以续跑，从最后完成的 step 接着执行。

Release 本身由 gate 管理，而不是手工完成。Release 是一个专用 commit，只包含 version bump、changelog entries 与新的 migration script。Release script 只有在全部检查通过时才允许打 tag：

- 记录的 versions 相互一致；
- changelogs 非空；
- migration script 存在且能解析；
- working tree 干净；
- 即将打 tag 的 commit 就是 release commit 本身。

它 fail closed：没有绿灯，就没有 tag。之所以加入这些 gates，是因为连续两个早期 release 漏发 migration scripts，破坏了升级链；现在的流程专门防止同一错误再次发生。

## 10 故障模式与加固

ATWZ 很多设计来自实际使用中的加固，而不是预先规划。本节汇总暴露出的 failure modes。部分问题已在前文单独讨论；集中查看时，它们展示的更重要内容是设计方法，而不只是某个 fix。

### 10.1 问题与缓解措施示例

- **重启后误以为 teammates 仍然存活。** `/resume` 恢复 session 后，lead 会向已经不存在的 teammates 发消息。→ 建立 liveness rule，并列出不能作为证据的信号（第 6 节）。
- **Respawn 漂移成 `Name-2`（旧版本）。** Persistent config 中的 ghost entry 与新 spawn 冲突。→ 在 respawn 前，用一个步骤清理并重建 registration。CC ≥ 2.1.178 的自动 session team 会在 teammate 退出时移除 ghost entries，因此不存在这一问题。
- **突然退出导致工作丢失。** Teammate 可能带着未保存进度进入 idle。→ 自动 idle-time checkpoint gate。
- **不同时区用户报告“timestamp 没更新”的误报。** → 比较 Unix epochs，而不是显示出来的本地时间。
- **两个团队使用同一个 role name 时，checkpoint nudge 路由到错误 workstation。** 旧版本通过 idle event payload 中的 team name（T1）解析；文档现在把该字段标记为 deprecated。CC ≥ 2.1.178 使用三级寻址链：先尝试 idle event 中的 team name（T1）；再使用 `<slug>-<role>` 名称的 slug prefix 推导 `${name%%-*}_team`（T2）；最后 glob 搜索，但若有多个 match，使用 exit-0 safety valve 放弃（T3）。
- **互相推诿归档。** 多个 recipients 情况下，resolved messages 从未归档。→ 把归档设为 issuer 的专属职责。
- **“热心”lead 重组 teammate 的文件。** → 建立 low-coupling rule，并在事故后扩展成明确子条款。
- **连续两个 release 漏发 migration scripts，破坏升级链。** → fail-closed release gates。
- **规则未到达最需要它们的 agents。** Rule list 位于各 `README.md` 的 user-owned 部分，升级不会刷新，导致安装副本相互漂移；上下文最容易填满的 teammates 反而没有落盘副本。→ 增加第二个由升级原地刷新的 marked block；`/spawn-team` 把精简 teammate 规则写进每个新 teammate 的 role file，并为旧 workstation 加入 self-heal step。

### 10.2 这份清单是什么，又不是什么

需要明确两点。第一，这只是持续使用中实际遇到问题的记录，不是设计完整性的证明。真正有价值的是循环：运行它、发现失败、把 fix 固化；这个循环仍在继续。

第二点是其推论：这样的 workspace layer 很难预先完全设计正确，因此吸收意外的机制与前期设计同样重要。本文不声称这份列表穷尽了全部问题，也不声称剩余 failure surface 很小；第 12 节会列出当前已知缺口。

## 11 相关工作

Agent Team Work Zone 借鉴了语言模型智能体领域的多条活跃研究路线。以下按主题组织，并说明本文增加了什么。

### 基础模型

本文关注的 agents 建立在 frontier LLMs 上：Claude Code 使用的 Claude [9]、OpenAI 编程工具背后的 GPT-5 family [10]，以及 Llama 3 等 open-weight families [11]。这些模型的广泛能力使开放式编程任务的委派成为可能。

ATWZ 的贡献与底层模型正交：它研究这类模型组成的团队如何长期保留状态。随着模型能力下限持续提高，这一问题仍然存在。

### 多智能体 LLM 系统

有一系列 frameworks 协调多个语言模型 agents 朝共同目标工作：

- AutoGen 把应用表示为可自定义、可使用工具的 agents 之间的对话 [12]；
- MetaGPT 按标准 operating procedures 驱动的软件开发流水线分配专业角色 [13]；
- CAMEL 研究成对 agents 之间的角色扮演协作 [14]；
- ChatDev 与 AgentVerse 分别把多个 agents 组织为虚拟软件公司，以及通用的协作与涌现实验平台 [15,16]；
- Multiagent debate 让多个模型实例经过多轮提出、批评和修订答案，以提高事实性和推理能力 [17]。

这些系统关注 agents 如何在一次 run 内分工和协调；ATWZ 的问题与其互补并且正交：让团队及其积累的状态在承载它的 session 结束后仍可重建。

### 持久化 Agent State

与本文最接近的，是已经把 agent state 写入持久存储、以便恢复工作的 frameworks。

LangGraph 用两个互补层持久化 execution state：checkpointer 在每个 super-step 保存 graph state snapshot，并限定于单个 thread，使 run 可以 resume 或 replay；store 则保存 graph state 之外、由应用定义的 key-value data，可跨 threads 读取，用于长期 facts 与 preferences [18]。

AutoGen 可以整体序列化 team。对 team 调用 `save_state`，会把所有 agents、group-chat manager 的 message thread 与 turn pointer，以及每个 agent 的 model context 保存成 dictionary；该 dictionary 可写入磁盘，稍后再加载 [19]。

这些系统持久化的是 execution 与其 residue：thread state、message history、context window；LangGraph store 还持久化应该跨 thread 的 facts。但它们都没有持久化一个**agency unit**。ATWZ 的关注点高一层：被持久化的不是 conversation 或 fact base，而是 teammate——它的 role、working notes、outstanding commitments 及 registry entry——从而使参与者本身而不只是它留下的记录，能在之后的 session 重建。

### 推理、行动与自我改进

许多 agent 能力来自组织单一模型的 reasoning 与 action，一项近期 survey 对此做了回顾 [20]：Chain-of-Thought prompting 引出中间推理步骤 [21]；self-consistency 对多条推理链采样并投票 [22]；Tree of Thoughts 搜索分支式 reasoning states [23]；ReAct 交替执行推理与工具 action [24]；Reflexion 与 Self-Refine 则在已有尝试上增加语言式自我批评和迭代改进 [25,26]。

这些方法塑造单个 agent 的 loop；ATWZ 提供的是文件式 substrate，使一支由这类 agents 构成的团队能够持久存在和协调。

另一条路线使 reasoning 本身更可控、更经济，让 agents 把 tokens 用在重要之处。Hybrid think/no-think models 暴露显式 reasoning switch，但两种模式并不会干净分离 [27]；可用专门的 architecture paths 将其解耦 [28]，或在无需训练的情况下引导到中间预算 [29]。用于推理的 reinforcement-learning post-training dynamics 还表现出顺序敏感与领域敏感 [30]。这些工作塑造 ATWZ agents 所运行的 reasoning substrate，与团队跨 session 持久化正交。同样的效率问题也延伸到 protein language models 等专用 family [31]。

### 工具使用

另一条相关路线教模型调用外部 tools 与 APIs：Toolformer 学习何时在文本中调用 APIs [32]；Gorilla 追求在大型、不断变化的 API collection 上准确调用 [33]；HuggingGPT 用 controller model 把 specialized models 作为 tools 编排 [34]；ToolLLM 把 instruction tuning 扩展到数千个真实 APIs，并配套 tool-use evaluation suite [35]。

ATWZ 本身也是一层很薄的 tools——hooks、scripts 与 skills——但研究对象是团队持久化，而不是工具调用。

### 记忆、上下文与 Agent Architecture

Context window 有限而且易失；模型甚至不能均匀利用长上下文，位于中间的信息会遭遇性能下降 [36]。因此，一些系统把 agent state 外部化：MemGPT 借用虚拟内存 paging，在上下文窗口与外部存储间移动信息 [37]；Generative Agents 维护可检索、可摘要的 experience stream [38]；CoALA 以模块化 memory 和结构化 action spaces 描述 language agents [39]。

ATWZ 认同“持久状态必须位于上下文窗口之外”的前提，但目标单位不同：整支团队的 roles、working notes 与 registry；目标 failure 也不同：session 结束会带走其中运行的 teammates。评估长期 memory 本身也很微妙；若按单条事实探测，主要 failure 往往不是没检索到证据，而是没有正确使用已经检索到的证据 [40]。

### Skill 获取与复用

Voyager 建立可重复使用、可执行的 skill library，并在需要时检索这些逐渐积累的 skills [41]。ATWZ 在 process conventions 与每 agent working notes 层面复用“可写入磁盘的能力”这一思想，而不是保存 task-specific code。一项近期 survey 从构建、组合、训练整合、安全到评估，梳理了 agent skills 的完整生命周期 [42]。

### 编程智能体

自主软件工程 agents 进展很快。SWE-bench 评估解决真实 GitHub issues 的能力 [43]；不同系统则在 autonomy 与 structure 之间采用不同权衡：

- SWE-agent 展示精心设计的 agent-computer interface 所带来的杠杆 [44]；
- OpenHands 提供通用、工具丰富的 agent platform，也支持一次 run 内多个 agents 的协调 [45]；
- CodeAct 把 agent actions 统一为 executable code [46]；
- AutoCodeRover 加入 program-structure-aware retrieval [47]；
- Agentless 说明固定、极简 pipeline 也能具有竞争力 [48]。

一项近期 survey 在 124 篇论文中梳理了这一 landscape [49]。Evaluation 也可以配置：agent benchmarks 能调整 task horizon 与 difficulty，同时降低 environment interaction 成本 [50]。

这些工作主要关注一次 run 内的能力，却很少讨论连续性：承载团队的 session 结束后会怎样，之后怎样恢复。ATWZ 正是处理这一缺口。

### 智能体基准测试

另一类工作测量 agents 能完成什么。AgentBench 在多种 environments 中评估作为 agents 的语言模型 [51]；交互式 environment suites 则在 Web、通用助理和完整计算机环境中提出 long-horizon tasks [52–54]。它们评估一次 run 内的 task capability，并与上述编程专项 benchmarks 互补。

### 本文增加了什么

LLM autonomous agents 和 multi-agent systems 的广泛综述，已经从 construction、memory、planning、communication、tool use 与 evaluation 等方面描绘这个设计空间 [55,56]。

在此背景下，Agent Team Work Zone 不是另一种 agent architecture，而是 persistence and management layer。它接收已有的 Agent Teams primitive，通过 files、checkpoints 和一键 reactivation flow，让团队跨 session 变得持久、可恢复、可审计。本文描述这些机制，而不是测量其可靠性。附录 A 进一步给出这些系统所处的 LLM 与 agent-harness landscape。

## 12 局限与未来工作

ATWZ 存在已知边界；明确说出它们，与本手册其余部分的态度一致。

一些局限是有意为之的 trade-offs。Idle checkpoint gate 在 teammate 尚无 checkpoint file 时 fail open，因此一个从未保存 checkpoint 的全新 teammate 不会收到自动 nudge。这是“有疑问时绝不阻止 teammate”的有意选择，却给刚 onboard 的成员留下缺口。

Checkpoint writer 与 reader 保持一致的 contract 目前只是文档约定，没有自动检查。开发者若修改一边却忘记另一边，会悄悄削弱恢复能力；增加 consistency test 会有帮助。

另一些是开放问题。两项内部检测依赖 text patterns 而不是 structured state：一是判断文档 completion checklist 是否全部勾选，二是判断 installer sections 是否已存在于项目 `CLAUDE.md` 中。

旧 API 曾有另两个问题，但已经随版本演进自然关闭。当时 reactivation 的第一步是清除并重建 team registration：

1. Clearing call 允许 no-op，因为刚重启的 lead 通常没有 team context 可清除；这是正常路径，不是功能退化，而 rebuild 失败则会终止运行。
2. Lead 必须推测按名 reactivation 是否应该跳过 clearing，因为 registration 无法查询。

2.1.178 移除了相关 tools，session-scoped team 也移除了这一步，所以当前版本不存在这两个问题。所有这些项目都不是隐藏事项，而是前述“发现并修复”循环中的当前记录。

最重要的是，本文提出的是设计，而不是评估。我们说明了机制和其背后的理由，也通过 ATWZ 的使用方式加以展示，但没有测量它们带来多少帮助、没有与替代方案比较，也没有研究人类如何与之协作。

未来工作的主要方向是实证评估：

- 在真实中断下的恢复可靠性；
- 这套工作纪律增加的 overhead；
- human-in-the-loop operation 的可用性；
- 更紧密的 lead/teammate protocol；
- 更低的 prompt-writing overhead；
- 保持框架足够简单，使 agents 能可靠遵守。

现有语言模型 evaluation methodology 可作为起点 [57]，但它主要测量 task quality，而不是这里关注的 recovery 与 continuity。更自主、把人类进一步移出 loop 的模式，要等模型能力足以被信任时再讨论。

## 附录 A：LLMs 与 Agent Harnesses 背景

第 11 节把 ATWZ 放在同层级系统中讨论：multi-agent frameworks、reasoning methods 与 coding agents。本附录后退一步，概述 ATWZ 所依赖的两层 substrate：使开放式编码委派成为可能的 model capability（A.1），以及把 model 变成 agent、再把一组 agents 变成 team 的 harness scaffolding（A.2）。ATWZ 位于二者之上，增加 persistence layer，并与这里列出的进展互补。

### A.1 大语言模型

ATWZ 协调的 agents 建立在大语言模型上，而其能力会随规模提高。Scaling laws 指出 loss 会随 model size、data 和 compute 以可预测方式下降 [58]；compute-optimal analysis 重新平衡 parameters 与 training tokens [59]；某些能力不是平滑提高，而是在越过规模阈值后才出现 [60]，这就是正文所称持续上升的“能力下限”。

原始 next-token prediction 之所以变得适合委派，来自两项转变。In-context learning 允许模型仅凭 prompt 中的少量 examples 执行任务，无需更新 weights [61]；一项 survey 追踪了这种能力如何工作，以及人们后来怎样理解它 [62]。Instruction tuning——用自然语言指令描述的任务做 finetuning——使模型能 zero-shot 地遵循未见过的指令 [63]；reinforcement learning from human feedback 则让输出与人类意图对齐，产生可以根据自然语言任务描述行动的 instruction-following models [64,65]。之后的研究通过直接优化 preference pairs 简化了 alignment，不再需要独立 reward model [66]。Lead 使用自然语言进行委派，依赖的就是这种能力。

效率同样是 agents 面临的现实问题，因为团队成本与延迟会随 model size 和每位 teammate 的思考时长增长。大量研究在降低语言模型 inference 成本：key-value cache paging 与 IO-aware attention 提高 throughput [67,68]；post-training quantization 降低训练后模型的 compute 与 memory 消耗 [69,31]；稀疏 mixture-of-experts architectures 以低于 dense model 的成本获得更大容量 [70]。ATWZ 在应用层的响应，是让每位 teammate 使用与其工作匹配的模型。

两项更广泛的研究给出完整图景：foundation models 框架描述向大型、适应性强的预训练模型的转变 [71]；另一项 comprehensive survey 则系统梳理了 LLMs [72]。

### A.2 Agent Harnesses

语言模型与实际工作的 agent 之间存在一层 harness：把一次性文本生成变成能够推理、调用工具和携带状态的循环。一项关于新兴 agent architectures 的 survey 梳理了本文涉及的选择：single-agent 与 multi-agent structure、leadership、communication，以及 planning、execution 与 reflection phases [73]。

ATWZ 位于这种 harness 之上一层。它不实现 loop，而是持久化 loop 产生的团队。

Harness 的一项能力是 tool use，使模型能通过调用外部 functions 与 APIs 行动。一项 survey 把 tool learning 描述为通用能力 [74]，第 11 节列出了具体方法。

另一项能力是 memory，使 agent 拥有超出单个 context window 生命周期的状态。一项 survey 梳理了 LLM agents 的 memory mechanisms [75]；第 11 节则把这些 agent-level mechanisms 与 ATWZ 的 team-level state 作了对比。

构成 harness 其余部分的 reasoning loops、cognitive-architecture framings 与 agent-computer interfaces 已在相关工作中说明。对这些系统而言，harness 负责运行 agent；ATWZ 增加的是把一支 agents 团队带过运行它的 session 的能力。

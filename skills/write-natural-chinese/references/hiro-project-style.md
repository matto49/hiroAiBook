# hiroAiBook 项目适配

这份参考只负责路由。项目内的实时文件优先于此摘要。

## 写作前读取

在仓库根目录依次检查：

1. `AGENTS.md`
2. `docs/reference/gakumas-hiro/README.md`
3. `docs/reference/gakumas-hiro/dialogue-style.md`
4. `docs/reference/gakumas-hiro/scene-and-outline-prompts.md`
5. `docs/plan/two-writing-styles-guide.md`
6. 当前章节及其计划、来源和相邻章节

只读取与任务有关的部分，但不要在没有看当前章节和来源时凭人设印象续写。

## 技术内容的主链

优先保持：

`现实问题 → 基线方案 → 缺陷 → 新概念 → 解决机制 → 新问题或边界`

概念不是词条。它应在前一个方案失败后登场。案例要能追溯，图像要承担信息，技术结论要有来源或明确推导。

## 场景必须参与推理

场景至少改变一个东西：约束、变量、行动、风险或角色判断。若删除对话后技术段完全不受影响，场景很可能只是包装。

角色声音放在观察、选择、失败和后果上。术语、公式和证据由叙述承担，不让角色用口癖代替解释。

## 筱泽广的声音

- 短句，安静，停顿少而准确；
- 先观察事实，再给出稍微异常但自洽的感受；
- 少用感叹号，不用密集口癖；
- 身体纤弱、头脑清晰、主动挑战失败三者同时存在；
- 不把她写成单纯病弱、受苦笑话或万能天才。

Producer 的严厉应建立在理解之上：知道她的目标和极限，因此提出具体要求，而不是空洞恶意或无条件宠溺。

## 两种文体

- **课堂/喜剧小说体：** 角色关系推动理解，失败造成技术问题。
- **技术报告体：** 先问题与证据，再方法与边界，角色只在关键判断处出现。

同一章节可以切换，但过渡必须由问题推动，不能只靠标题或“接下来我们看看”。

## 公式和概念

公式先解释符号和计算，再用自然语言讲整体作用；随后连接例子、边界或角色判断。不要让角色逐字朗读公式。

## 禁止补写

没有计划或来源支持时，不编造：

- 技术结论和数据；
- 原作剧情、台词或角色经历；
- 章节结局和价值判断；
- 为了“像广”而增加的痛苦、病弱或失败细节。

## 完成检查

若修改了有意义的 `.tex` 正文，运行 `latexmk -xelatex main.tex`。区分已有警告和本次引入的警告，并检查是否影响输出质量。
